docs/adr/0006-runtime-lifecycle.mdgateway/src/lifecycle.ts:L66-L200gateway/src/model.ts:L21-L23

状态：M1 决定。取代 ADR 0002。

决定：请求、流式响应、WebSocket 或 SSE 连接、触发执行都是 Lease。实例状态机 asleep / waking / awake / draining / stopping 每实例一把锁，awake -> stopping 只在 Lease 为空时发生，acquire 在同一把锁内加 Lease。客户端断开不提前释放 request Lease。只有发布、remove、purge 引起的 draining 会主动结束 Lease。发布是写一条不可变 Release 并移动 App.current，release_key 相同为空操作。平台状态是 /data/pneuma-space.sqlite3 一个文件，每张表一个写者。内部资源和容器以不透明的 App.id 命名，name 只用于地址，M3 的租户只需改 name 到 id 的查找。容器名 pneuma-space-<id>-<release> 确定，标签带 Injection 哈希，创建和启动可重复，启动时据标签识别过期容器；唤醒后 inspect 一次缓存 IP。

理由：INV-3 只需要一个证明。网关和调度器共用一个动词 acquire，所以唤醒路径只有一条。每实例锁消灭全局锁。SQLite 让发布在一个事务里写 Release、Trigger、Binding 和指针，JSON 文件做不到。缓存 IP 绕开 Docker DNS 对外部停止容器约 4 s 的失败。

拒绝：事件溯源控制面（为证明幂等多出投影机制）；每 App 一个 actor 持有全部状态（列表和触发查询变成 scatter-gather，崩溃丢内存真相）；发布时拒绝有活动请求的 App（有一个长连接的 App 永远发不了）；原型的 http.server 直接扩展（线程和锁纪律随每个能力恶化）。

后果：一个开着的 WebSocket 让 App 保持唤醒，由 connection_idle_seconds 兜底。发布后最多 drain_timeout_seconds 切断剩余请求并关闭连接，换来一个 App 只有一个进程打开 /data。网关重启丢失 Lease 和连接，客户端重连，触发重投。

  4. 存储绑定中立。 Injection 不再带 Docker volume 名和挂载点，而是"这个应用需要的持久目录"列表（files、db 的 sqlite）；容器运行时把它落成 volume 挂载，isolate 运行时落成 runner 卷里的 /data/apps/<id>/<kind>/。Provider 的四个动作不变，由运行时各自实现落地：容器运行时在创建容器时建 volume 并挂载，isolate 运行时让 runner 建目录；destroy 经 Runtime.destroyStorage 删掉它。Provider 的 ensure 只记录绑定，不碰后端。
  5. runner 是独立服务。 在平台网络上开一个内部端口，不发布到宿主机；网关的 IsolateRuntime 通过它起、停、列出实例、取事件。每个应用一个 worker_threads Worker，不传 execArgv（实测 Node 24：任何 execArgv 都会丢掉继承的 --permission，而 --permission 本身已禁止原生扩展），resourceLimits 封顶内存，各自在 runner 容器里监听一个端口，网关像转发到应用容器一样转发到 runner:<port>。起 worker 时网关把 bundle 的预签名 GET 地址交给 runner，runner 自己下载解包到它的卷，不持有对象存储凭据。网关重启向 runner 收养在跑的实例；runner 重启（启动时间变化）后网关把它的实例标回 asleep。runner 未启用时，发布 isolate 应用答 409，总览服务条显示 runner 未启用，和 coturn 一致。
  6. 探活是运行时的事，判定和后果是平台的事。 容器运行时靠 Docker 事件和就绪探测；isolate 运行时在 runner 里对每个 worker 每秒 MessagePort 心跳，3 s 无应答即 terminate()（V8 TerminateExecution，能打断同步死循环；不能打断阻塞的原生调用，见理由），堆内超限由 resourceLimits 触发退出，堆外（Buffer）由心跳附带的 process.memoryUsage() 按 worker 采样、超预算即 terminate()，uncaught 和 exit 由事件报告。terminate() 5 s 未返回的 worker 记为 stuck：实例按退出上报、端口释放、同一应用可起新 worker，runner 只在 stuck 数超过预算时重启；runner 从不因为一个 worker 退出。 runner 主线程是所有 worker 共享的，对每个 worker 只做有界的工作：日志在垫片里按行截断并限速后才经消息口送达，runner 对 worker 原生 stdout 流只计数不分行；看门狗的迟到按迟到量顺延未答心跳的期限而不是清零，所以主线程短暂迟滞只推迟判定、不会掩盖卡死；垫片同时禁掉 v8.setFlagsFromString（进程级标志能让 %AbortJS 终止整个 runner）并收走 parentPort。 runner 把 worker 发来的每条消息当不可信输入：校验形状，不合法的丢弃并记事件；垫片在加载时绑定自己端口的方法，并用自己的流替换 process.stdin、stdout、stderr，让 Node 的 stdio 内部端口不可达；runner 进程装 uncaughtException 处理器，记一次 internal 故障后继续运行。runner 从不因为一条消息退出。 已知边界：async_hooks 的 executionAsyncResource() 能让应用拿到垫片的端口和 Node 的内部端口，这是蓄意行为；防线是让拿到端口也无害：listening 只认 runner 分配给该 worker 的端口，Worker 的 error 事件一律 terminate 并保持看门狗到 exit，每条消息按索引校验元素类型。拿到端口的应用最多能伪造自己的心跳，骗过的只是对它自己的卡死判定。平台一处实现统一策略，进 Policy 可全局和按应用改：重启退避秒数、时间窗内允许的失败次数；超过即隔离。Instance 多一个 quarantined 属性（原因、时间），被隔离的应用 acquire 答 503，直到新发布或运营者在后台解除；每次失败和隔离都是生命周期事件，进收件箱，算唤醒失败。五个状态的状态机不变。
  7. 脚手架。 templates/app 成为 isolate 脚手架（清单 runtime: isolate，入口 src/server.ts，监听环境变量给的端口，无 Dockerfile）；templates/container 是同一套 SDK 加 Dockerfile；templates/static 不变。appctl init 默认 isolate，--container 和 --static 可选。isolate 应用的发布：appctl 在开发机上 npm ci --omit=dev --ignore-scripts，连 node_modules 打成 bundle 上传，和静态站同一条路，网关不跑 npm。这个 bundle 是整个应用目录：声明了 static 时平台只从其中 static.dir 子树答静态文件，未声明则不答任何文件；容器发布的 bundle 仍是 static.dir 子树本身。示例作为脚手架的覆盖层随之跑在 isolate 上。

理由：spike S4（spike/isolate/findings.md，macOS，Node 24 和 25）：一个加载模板 SDK 的 worker 从创建到首次 HTTP 应答中位 42 到 48 ms，子进程 72 到 75 ms，容器实测约 200 ms；每个 worker 使宿主 RSS 增加 17 到 18 MiB，子进程 78 到 84 MiB，容器约 35 MB；loopback 延迟中位 85 到 98 µs；while(true){} 在 3 到 4 s 内被心跳发现，terminate() 约 1 ms 完成；堆超限约 60 ms 内以 ERR_WORKER_OUT_OF_MEMORY 结束；未捕获异常和 process.exit 只结束该 worker；所有演练中其他 worker 没有一个请求失败。spike 也量出三条逃逸，决定里的防线对应它们：阻塞的原生调用（如 execSync）terminate() 要等它返回，所以 runner 以 --permission 启动、不授予 child_process，terminate 超时的 worker 记为 stuck 留在那里，runner 只在 stuck 超过预算时重启（2026-11-05 修订：原先是 terminate 超时 runner 即自行退出，那会让一个应用带走所有 isolate 应用）；1 GiB 的 Buffer 不受 resourceLimits 约束，但 worker 自己的 process.memoryUsage().arrayBuffers 和 external 按 isolate 计（实测 512 MiB Buffer 只出现在持有它的 worker 上，主线程和空闲 worker 报 0），所以心跳采样超预算即 terminate，runner 容器的操作系统级内存上限只作兜底；worker 里 process.kill(process.pid) 能杀宿主，所以每个 worker 的主脚本是 runner 自己的一段垫片（gateway/src/isolate-shim.ts）：移除 process.kill 和 process.abort、应答心跳、把 drain 转成 SIGTERM，然后再加载应用入口（实测 Node 24 的 Worker 忽略 execArgv 里的 --import）。Atomics.wait 实测可被 terminate() 打断，stuck 的真实触发只剩阻塞的文件读等系统调用。两个堆上限（old 和 young）都显式设置，宿主对每个 worker 挂 error 和 exit 监听。Node 的 worker 就是 V8 isolate，不需要新运行时；发布从构建镜像变成拷目录，是 Agent 开发者最常走的那段路；runner 独立部署，故障域和网关分开，也是 M2 在工作节点上跑的那个东西。

拒绝：进程内 import() 到网关（没有隔离，一个应用拖垮全部）；每应用一个子进程的 ProcessRuntime（代价和容器相近，隔离更弱，用户不要）；workerd 作为 M1 运行时（应用契约整个换掉，SDK 重写，多一个二进制；作为未来的第三种运行时保留）；runner 作为网关的子进程（用户要求独立部署）；worker 之间的 fs 和网络限制（可信主机，容器才有）；原生扩展（--no-addons，一个段错误会带走整个 runner）。

后果：compose 多一个 profile 服务；Injection 和 RunSpec 的类型变化要过一遍 Provider、注册中心、CLI；AGENTS.md 多一条结构规则；app-contract 多一节 isolate 应用契约（端口来自 PNEUMA_SPACE_PORT，纯 JS 依赖，有文件系统）；验收加 AC-ISO 行。将来 workerd 运行时是同一张表的第三行，它的实例可以在云端，Provider 的落地变成云端绑定，身份若要不经网关直达边缘另立 ADR。

  5. 唤醒、休眠、日志、收养。 唤醒：按 StorageBinding 确保 PVC（409 视为已存在），删掉同名的残留 Pod（崩溃留下的 Failed Pod，先取日志），创建 Pod，从本副本的 Pod watch 等容器进入 Running，然后每 50 ms 对 podIP:8000 做 TCP 探测直到就绪或 ready_timeout_seconds；就绪计时从容器 Running 起算。Pending 超过 PNEUMA_SPACE_K8S_PENDING_SECONDS（默认 60）即以 Unavailable 失败，Guard 不计数：Unschedulable、拉镜像失败、卷挂载慢、节点丢失后的 Multi-Attach 都是集群的事，不是应用的。等待期间 Pod 进入 Failed 才是应用的失败，原因取 terminated。不用 kubelet 的 readinessProbe，它的周期至少 1 s。休眠和退役是同一个动作：取最后 200 行日志（上限 64 KiB）写进 instance_log，删 Pod（带 uid 前提），等 watch 送来 DELETED；K8s 没有"停止的 Pod"，handle 不跨休眠保留。Pod 所在节点 NotReady 时它会一直 Terminating：等满 drain_timeout_seconds 后，若节点带 node.kubernetes.io/out-of-service 污点（运营者确认节点已隔离），平台强制删除（gracePeriodSeconds: 0），否则继续等，应用在节点恢复前不可用。运营者维护节点用 cordon 而不是 drain，drain 会拒绝不受控制器管理的 Pod。转发前，副本核对自己 watch 缓存里这个 IP 对应的 Pod uid 等于实例行的 handle，缩小 Pod IP 被复用的窗口。日志：Pod 在时读 pods/<name>/log，不在时读 instance_log，任一副本都能答。收养：网关重启不碰 Pod，领导者按 pneuma-space.role=instance 列出 Pod 与实例行比对 app、release、spec、epoch，不一致的删掉。health() 是 ['exit', 'ready', 'memory']，OOMKilled 报为 memory。
  6. 镜像来自组织的仓库。 appctl publish <name> <image> 先 docker push 到 PNEUMA_SPACE_REGISTRY，再发引用；网关 resolveImage 对仓库做 OCI distribution 的 HEAD /v2/<repo>/manifests/<tag> 取 Docker-Content-Digest，认证读 PNEUMA_SPACE_REGISTRY_AUTH 指向的 dockerconfigjson，支持 Basic 和 Bearer 换取。Release.image 存 <registry>/<repo>@sha256:...。平台不自带仓库，不发自己的镜像。
  7. /data 是每个 StorageBinding 一个 ReadWriteOnce PVC，名字 pneuma-space-files-<id>、pneuma-space-db-<id>，在应用命名空间，首次唤醒创建；storageClassName 取 PNEUMA_SPACE_K8S_STORAGE_CLASS（空为集群默认），容量取 PNEUMA_SPACE_K8S_VOLUME_SIZE（默认 1Gi；租户的 storage_gb 按这个已供应容量计，ADR 0023）。调度器按 PV 的拓扑约束放 Pod，平台不记节点。remove 不碰 PVC；purge 先退役实例再删 PVC 并等它消失，30 s 内没消失抛 Conflict，purging 下次续跑重试。PV 的去留由存储类的 reclaimPolicy 决定。
  8. isolate 的 runner 是 StatefulSet，副本数由运营者定，preferred podAntiAffinity 按节点分散，volumeClaimTemplates 给每个副本一个 RWO PVC 作 /data，内存上限和 --permission 参数与 compose 相同。网关 watch pneuma-space.role=runner 的 Pod，地址 podIP:8082，就绪由 runner 的 readinessProbe GET /health 给出。每个 isolate 应用首次唤醒时选醒着 worker 最少的就绪 runner 作 home，在 waking 的 CAS 里写进实例行，以后只在它上面跑；一条规则，不分有没有存储。home 不可达抛 Unavailable，答 503，Guard 不计数。runner 的 Pod automountServiceAccountToken: false，只有网关能到它（第 10 条），控制接口不另加令牌：同一 runner 里的 worker 共享进程，任何给 runner 的秘密 worker 都读得到。runner 给 worker 分配端口按轮转加冷却期，不让一个刚结束的 worker 的端口立刻被下一个拿到。
  9. 按子域名取应用名。 PNEUMA_SPACE_APPS_ORIGIN（如 https://*.apps.example.com）设了就是子域名模式：Ingress 从 Host 去端口、转小写，要求恰好 <label>.apps.example.com，label 按应用名文法解析，整条路径交给应用，X-Forwarded-Prefix 发空串（头存在，值为空），没有 308 补斜杠。没设就是 M1 的路径模式。一个部署只有一种模式，列表和控制台的 address 由同一个函数给出。public 应用怎么让上游放行匿名访问是运营者的上游配置；给 public 应用第二个域名会把它的 cookie 分成两份，M2 不做。组织入口把 *.apps.example.com 转到 Service pneuma-space-gateway 的 8080，控制台主机转到 8081，TLS 在入口终止；入口的读超时不小于 connection_idle_seconds，否则 WebSocket 和 SSE 被入口切断。

理由：平面而不是运行时，因为 container 和 isolate 在 K8s 上还是那两种东西，变的只是谁起容器和状态放哪里，第三行运行时会让 Provider 和清单无端看见部署形态。Pod 而不是 Deployment，因为平台自己决定唤醒和休眠，控制器的 reconcile 会和休眠判断打架（已定取舍 6）。两个命名空间而不是每租户一个，因为 App.tenant 可以移动而 PVC 不能跨命名空间，配额要在发布和唤醒时以可读的原因拒绝、平台自己算（ADR 0023），实例间隔离本来按 Pod 做，RBAC 和 NetworkPolicy 因此是固定几份 YAML。RWO 而不是 RWX，因为一个 App 同时只有一个实例，SQLite 的 WAL 和文件锁在 NFS 一类存储上不可靠。StatefulSet 而不是 DaemonSet，因为 DaemonSet 不能每个 Pod 一个 PVC。网关自己探 TCP，因为 kubelet 探测把就绪推迟到秒级。digest 引用，因为 tag 会动而 Release 不能动。

拒绝：每租户一个命名空间（见理由，留给 M3 的对抗性隔离）；每应用一个 Deployment 或 StatefulSet；runner 用 DaemonSet 加 hostPath（数据绑死节点）；默认 RWX；K8s readinessProbe 和 restartPolicy: Always（kubelet 在 Guard 看不到的地方重启）；每应用一份 NetworkPolicy（上万个对象）；平台自带镜像仓库（已定取舍 5）；exec 进常驻工具 Pod 做供应（要用内置模块实现 exec 的 WebSocket 子协议；供应怎么做见 ADR 0025）。

后果和已知限制：云块存储在 Pod 换节点时先卸载再挂载，常见 10 到 60 s，可能破掉首请求 5 s 的目标，bench 量出来超了再加"偏好上次节点"的软亲和。节点本地存储把带 /data 的应用钉在节点上，US-O-4 以能跨节点移动的存储类为前提（REQUIREMENTS-M2.md）。K8s 的新卷不继承镜像目录的属主，靠 fsGroup，契约加一句。Pod IP 被复用的窗口由转发前的 uid 核对缩到 watch 延迟，没有消除。同一 runner 里的 isolate 应用共用 Pod 网络，出向隔离到 runner 为止，而且它们能经 localhost 直连彼此的 worker 端口并伪造身份头，INV-5 对同一 runner 里的应用之间不成立（REQUIREMENTS-M2 信任边界写明）。PNEUMA_SPACE_PLANE=kubernetes 配 PNEUMA_SPACE_IDENTITY=local 拒绝启动：local 不认证管理 API，靠的是回环绑定，Service 没有回环。网关能在应用命名空间建任意 Pod，网关失守即命名空间失守，Pod Security baseline 是边界，符合 M2 的信任边界。缩容 runner 会让 home 在被删副本上的应用不可用，M2 只支持扩容。

一把会话级 advisory lock pneuma-space.leader；行锁 FOR SHARE 和 FOR UPDATE；instance 和 guard 的每次写由行触发器在提交时发通知，通道 pneuma_space，载荷 instance/<app id>（ADR 0025）。lease_tally 不发通知：PostgreSQL 把所有发过 NOTIFY 的事务的提交串在一把全局锁上，租约边沿不能排进去；正确性从不读租约镜像，只在事务里读行。Registry 的变更走同一通道，其他副本据此重建 RouteView。每个 CAS 的谓词都带 runtime：一个 App 只有一行，container 和 isolate 两个 Lifecycle 都读它。

  1. 每个副本在内存里维护三张表的镜像。 instance 和 guard 收到通知就重读那一行；lease_tally 每 5 s 重读一次只供显示；监听连接重连后全量重读；每 30 s 全量重读一次兜底。Runtime 的同步读接口 state、since、leases（本副本的实时计数加其他副本最近一次读到的计数）、sleepsAt 和 Guard 的 quarantine 都读镜像，列表仍然零 IO（AC-P-8）。
  2. 流程。 每个 CAS 带 WHERE app=$1 AND state=<预期> AND epoch=<预期>，然后发通知。
  • acquire 快路径：镜像里实例 awake，本副本对当前 epoch 最近一次已提交或已排队的 tally 大于 0，本副本的 watch 没报这个 handle 结束：内存里加租约，零 IO。热请求都走这里。一个副本对一个 App 的所有 tally 写经一条本地队列，入队时就记下计数，所以"排队中的 0 写"和新租约不会交错出一个被回收器误判的 0。
  • acquire 慢路径，实例醒着：一个事务 SELECT ... FOR SHARE，awake 则 upsert 本副本的 lease_tally 使计数大于 0。这是 0 到大于 0 的边沿，同步写库，和回收器的 FOR UPDATE 互斥，所以不会被睡掉。
  • 唤醒：一个事务里先读 app 行的 version、status、current（ADR 0025：Registry 的每次写都把 version 加一）。本副本 RunSpec 的 version 落后就放弃唤醒、刷新视图再来，status 不是 active 就按 M1 答 404，所以过期的视图唤不醒旧版本，也唤不醒已移除的应用。然后 UPDATE instance SET state='waking', epoch=epoch+1, actor=$me, runtime=$runtime ... WHERE state='asleep'（没有行时先 INSERT ... ON CONFLICT DO NOTHING），读 guard 行做准入（隔离和退避答 503），锁租户行做配额准入并写入这次的 cpu_millis、memory_mb（ADR 0023）。准入是 Lifecycle 拿到的一个回调 admit(tx, spec)，由 Guard 持有，Guard 仍是唯一计失败和隔离的地方。赢家调用 driver.start，再 CAS 到 awake，写 address、awake_at 和自己的计数。输家和其他副本等这个 app 的通知，每 500 ms 轮询一次行兜底。启动失败 CAS 回 asleep 并发失败事件。事务体可能被重跑（ADR 0025 第 3 条），所以事件只在提交后发。
  • release：只改本地。计数降到 0 或分类计数变化时，最多 1 s 后写一次 lease_tally（写 released_at）；draining 时立即写。
  • 回收（领导者）：每 min(idle_seconds, 10) s 扫镜像里 awake 的行；候选行开事务 FOR UPDATE，确认当前 epoch 没有计数大于 0 的行且 now - max(released_at, awake_at) >= idle_seconds，CAS 到 stopping；锁外 driver.sleep，再 CAS 到 asleep。
  • 退役：由执行发布、改策略或 remove 的副本在提交后直接做。CAS awake→draining 并发通知；每个副本看到 draining 就对本地 channel 调 onRetire 并立即写计数；退役方等计数之和为 0 或 drain_timeout_seconds，然后 CAS stopping、driver.remove、回 asleep。新 Release 的 Pod 在旧 Pod DELETED 之后才创建，"两个进程不同时打开一个 /data"仍然成立。
  • 实例自己结束：每个副本都 watch Pod、轮询它看得到的 runner，观察到结束就 CAS awake→asleep WHERE epoch AND handle，只有赢家发 crashed 或 hung 事件，Guard 每次失败只记一次。
  • 接管：启动时每个副本先删自己旧的 replica 和 lease_tally 行（新进程不持有任何租约），再接管 actor 是自己的 waking、stopping、draining 行；领导者每 5 s 接管 actor 的 seen_at 超过 10 s 的行。接管按确定的名字删 handle，CAS 到 asleep；draining 行接着排空。晚到的原唤醒者 CAS 失败，它创建的 Pod epoch 不匹配，由孤儿清理删掉。副本 id 是 Pod 名，容器重启后不变，所以 actor 活着不等于那次转换还有人管，启动接管补这个缺口。
  • 孤儿清理（领导者，取得领导权时和之后每 60 s）：驱动列出的实例，若列出后读到的行既不指向它的 handle 也不是 waking，就删掉；isolate 不参与，它的孤儿 worker 由 recovery poll 停掉。
  • 领导者：一个专用连接持有 advisory lock，会话设 tcp_keepalives_idle=10、interval=5、count=3，每 2 s SELECT 1，带 3 s 的客户端超时，超时或失败即卸任并停下领导者的循环，所以半开连接上的旧领导者在服务端释放锁之前就已经停手。领导者跑回收器、Scheduler、接管、孤儿 Pod 和 worker 清理、死副本行清理、Provider 收敛、ADR 0024 的采样和清扫。Scheduler 的认领是条件更新 UPDATE delivery SET state='delivering', replica=$me WHERE id=$1 AND state='due' 并检查行数；取得领导权时只把 replica 已死的 delivering 行放回 due，不是全部。
  1. Guard 跨副本。 状态从内存 Map 搬到 guard 行。失败只由 CAS 赢家或唤醒者记录，在 FOR UPDATE 事务里过滤时间窗、追加、判定隔离。unquarantine 删行并发通知。规则和 Policy 字段不变。
  2. 副本优雅退出。 readiness 先失败，preStop 等 5 s 让 Endpoints 收敛，再关连接、删自己的 lease_tally 和 replica 行。流经它的 WebSocket 断开，客户端经别的副本重连，和 M1 重启的后果相同。
  3. 单机 Compose 是 N=1 的特例。 领导锁立即取得，通知是进程内事件，SQLite 的 transaction 本来独占。启动时按 pneuma-space.role 标签列容器，与实例行比对，规则同 ADR 0019 第 5 条的收养。不保留一份内存版 Lifecycle，两份状态机迟早漂移。
  4. purge 的清理在每个副本上做。 收到 app/<name> 通知而行已不在，副本丢掉本地视图和状态；拥有 instance、lease_tally、guard、instance_log、stats 行的组件各自删掉该 App 的行（删除幂等，多副本重复无害）。deleteApp 只删 Registry 自己的表。

  2. isolate worker 归谁，只看库里的行。 worker 有主，当且仅当它的 App 的 instance 行（在 runner 列出之后从库里读）runtime 是 isolate，并且 handle 是它而行不是 asleep，或者行是 waking（唤醒者可能还在创建它）。这是 ADR 0020 第 4 条孤儿清理的规则加上"不是 asleep"：isolate 不跨休眠保留 worker，asleep 行上留下的 handle 只是一次没停成的 worker。判定只在 recovery 一处：领导者每 5 s 对每个答话的 runner 做一次，任一副本在自己对某个 runner 的调用失败后、该 runner 再答话时做一次。列出后，镜像认为有主的直接留下，其余逐个读库，确认无主才停。停是有条件的 DELETE /instances/<app>?worker=<id>：runner 只在该 App 当前的 worker 正是这个 id 时停它、清它的代码目录和日志。按 handle 删 worker 的其他路径（唤醒失败、接管、退役、收养）也带 id。领导者启动时的收养（ADR 0019 第 5 条）只比对库里的行指名且不是 asleep 的 worker，其余留给 recovery。recovery 可以重复做，两个副本同时做，结果相同。
  3. 每个副本跟随每个醒着的 isolate worker 的结束，不论谁起的。 跟随的集合由镜像推导：awake 的 isolate 行，home 是这个 runner，handle 是这个 worker。runner 的事件流按游标读；游标读到过一个 worker 的 ready 事件，它之后的结束就一定读得到。否则（刚开始跟随、游标有断档、runner 换过进程）先清点一次 runner 的 /instances：worker 在列，就算接上了；不在了，用 runner 还留着的终止事件归类，没有就记为 crashed 并写明原因。然后照常 CAS awake→asleep WHERE epoch AND handle，只有赢家记 Guard 失败、发事件。runner 连续 15 s 不答时，副本只把自己起的或收养的 worker 标为 unavailable：答不答是这个副本的视角，不是 worker 结束了。

理由：快路径发出的租约要被库里的计数保护，回收器的 FOR UPDATE 只看得到已提交的行，排队中的正数挡不住在它提交前抢到行锁的回收器；R1 实测第二个请求在首个 tally 提交前已被转发。等待者共用那一笔写，热应用的冷边沿仍只写一次。本地集合缺项只说明这个副本没起那个 worker；R2 里副本 B 的恢复停掉了副本 A 持有租约的 worker。行是唯一跨副本一致的归属，container 的孤儿清理早已按它判。起 worker 的副本会死；R3 里领导者接任后没有副本看见 worker 退出，行一直 awake，请求 502。ADR 0020 第 4 条本来就要求每个副本轮询它看得到的 runner，用 ready 事件判断游标是否覆盖，平时不必清点。

拒绝：每个 worker 一个属主副本（ADR 0020 已拒绝）；recovery 凭镜像判无主（镜像可能落后于刚完成的唤醒）；把 isolate 接到 Driver.list 和领导者 60 s 的 sweep（孤儿要等到 60 s，而 sweep 留下 asleep 行指名的实例，Pod 靠这一点留住崩溃日志，isolate 不该留）；每个 acquire 各等各的事务（同一 epoch 的并发请求各开一个事务）；runner 不答时每个副本把它上面所有 worker 都标为 unavailable（一个副本的网络故障会让别的副本持有租约的应用休眠）。

后果：DESIGN 2.3 的快路径和结束观测指向本 ADR。领导者对每个 runner 每 5 s 多一次 /instances；副本接上一个游标没覆盖的 worker 时多一次 /instances。孤儿 worker 在 5 s 加一次停止（排空至多 10 s）内消失。runner 会复用同一 release 和 spec 的 worker（重试的启动加入正在跑的那个），所以按 id 的条件删除挡得住新 epoch 起的新 worker，挡不住在同一毫秒级窗口里被新唤醒复用的孤儿：那次唤醒表现为一次 stopped 结束和下一个请求的重新唤醒，不计失败。runner 只对一个副本不答时，别的副本起的 worker 由它们自己标 unavailable；起它的副本已死而 runner 又不答时，行要到闲置回收才休眠。

理由：只比较 seq 大小，新进程的 seq 追上旧游标之后就认不出重启，它还保留的前若干条记录被静默跳过，页面却像一条连续的流。世代给"同一条流"一个身份，判断不再依赖 seq 的大小。启动毫秒够用：同一副本名的两次启动之间隔着一次进程启动，不会落在同一毫秒；usage 的 replica 列已经用启动毫秒区分重启（ADR 0024 第 2 条）。reset 由持有那条环的副本自己判定，判定只读内存，GET /api/requests 仍然零 IO（AC-P-15）。

状态：接受。2026-11-11。

背景

ADR 0033 让下线使旧发布失去激活资格，但元数据的序号不能撤销已经发出的对象写入。真实文件适配器复现了这个顺序：发布停在写制品之前，下线和清除完成，旧写入随后落盘。应用没有复活，源代码却重新出现。写入后再检查无法覆盖写入完成后进程消失的情况。

决定

ArtifactStore 拥有每个 AppId 的不可变制品键登记和永久清除标记。Cloudflare 适配器在独立的每应用 SQLite Durable Object 中先登记摘要，再向 R2 做仅当键不存在时的写入。清除先原子关闭登记，再将所有已登记的 R2 键覆盖为不含代码的终态标记。旧写入先成功时，清除覆盖它；终态标记先成功时，旧写入的条件失败。未完成的清除可以重复执行，不删除登记或标记。

登记只在保存制品和清除时访问。读取制品不经过它。该状态属于 ArtifactStore，不属于 RecordsProvider，也不进入应用 ABI。替换适配器必须提供相同的终态保证。本地文件适配器使用 SQLite 事务串行化终态检查和同步文件写入、删除。

每次实际重试准备制品都重新消耗当天的发布额度。已经成功的幂等重放不消耗额度。应用数和制品字节的容量预留仍按逻辑操作去重。

后果

清除删除应用数据与代码字节，保留拒绝迟到写入所需的少量终态元数据。Cloudflare 增加一个仅用于制品登记的 Durable Object 命名空间。不增加后台清理任务，也不依赖调用者在错误后继续运行。

状态：接受。2026-11-12。用户明确要求保留全部 M1、M2 应用能力和管理功能。

背景

ADR 0033 的独立 Fetch 入口只覆盖受限应用契约。实现又新建了精简控制台，既没有原有观测数据，也没有呈现已有的审计和版本历史。运行时实验因此被当成了完整 SaaS，违背用户要求。

决定

SaaS 使用现有 Node 网关、Registry、Store、Runtime、Provider、Scheduler、Metrics 和控制台。新增 hosted 身份模式，local 和 upstream 的语义不变。后端选择不能缩减 M3 需求 的产品基线。Fetch 契约保留为独立实验，不替代契约 1。

托管登录由新的身份实现负责，先支持 GitHub。Registry 在同一平台库事务内登记不可变外部身份、用户、个人租户及管理员成员关系。已有身份不受新注册容量限制。Sessions 是登录握手、控制台会话、应用会话及一次性授权码的唯一写者。SQLite 与 PostgreSQL 使用同一组 Store 操作，不另建云端应用目录。

控制台和应用分别使用主机专属会话。应用登录经过绑定 AppId、精确源、父会话及浏览器随机值的一次性交换。退出使派生会话的下一次准入失效。控制台写入检查精确 Origin 和会话 CSRF 值。应用身份头、cookie 和 Bearer 凭据经过现有入口过滤，应用响应不能设置平台保留的 cookie。

新注册不授予平台管理员。运营者仍由 PNEUMA_SPACE_PLATFORM_ADMINS 指定。首次发布默认私有，现有应用的访问设置不迁改。令牌的到期时间、动作和 AppId 范围与原有权限取交集，旧令牌保持原权限。发布在激活前重新检查托管会话或令牌。管理、静态内容、动态请求、WebSocket 及触发入口使用同一授权规则。

完整平台继续提供原观测和运维视图。用户只看其权限内的应用和租户，平台管理员看全局。新增账户入口与凭据控制在原控制台实现，不再维护另一套完整产品界面。

验证与部署

新增行为和原功能回归由 SaaS 验收 定义。开发身份只能在明确的本地模式启用。正式托管登录需要身份提供者配置和独立的控制台、应用站点。

本决定改变登录方式，不改变已有运行时的信任承诺。完整能力在可信的本地环境及组织部署验证。面向不可信代码的公开注册还需要独立验证计算、网络、数据和控制面隔离。命名空间、网络策略和共享 runner 不能单独建立该保证。

取舍

选择在现有身份接缝增加实现，避免另一项服务与网关之间重复持有账户和授权状态。代价是网关增加登录和会话职责；这是对 M2 不实现登录的显式扩展，不改 M2 的部署模式。

Cloudflare 可承载适用的入口或存储服务。任何入口都必须通过原有流式请求、WebSocket、SSE、对象直传及 RTC 检查，不能用 Fetch 示例通过代替完整协议验证。

背景

G14 的首个云后端需要保留 契约 1。Cloudflare 普通 HTTP 代理的上传上限与源站超时不能承载全部既有请求。DNS-only 流量直接到源站，不经过 Cloudflare 的代理、WAF 或缓存。代理行为、连接限制。

现有托管 Ingress 示例依赖社区 ingress-nginx。该项目已于 2026-03-24 退役，不再接收安全更新。Kubernetes 说明。

决策

  1. 先交付 Cloudflare DNS-only 与源站 TLS 的兼容性单元。控制台、应用和对象域名直接解析到源站。真实 Cloudflare 边缘转发仍待付费四层方案验证，不能据此关闭 G14 或公开发布门槛。
  2. 一份 Caddyfile 定义控制台到网关 8081、应用到网关 8080、对象到 S3 9000 的路由。它读取现有公开 origin；部署配置提供三个内部 upstream。Kubernetes 用 ConfigMap 装载同一文件，替换已有 Ingress。本地独立 Compose 环境装载同一文件做协议验证。不给网关添加依赖或厂商接口。
  3. 保留外部 Host、原路径、查询和 Origin。不开缓存、压缩、请求体缓冲或体积上限。响应使用正数刷新间隔，保留客户端断开后的上游取消。未知主机不能落到应用路由。证书由运营者提供，DNS-only 必须使用浏览器信任的证书，不能使用仅供 Cloudflare 回源的证书。
  4. TURN 的监听端口与 UDP 中继范围独立公开。镜像仓库保持既有推送、摘要查询和节点拉取接口。二者不能被 HTTP 入口替代。
  5. 计算、卷与平台服务保留既有拥有者。M3 的恶意代码隔离、后端资源预算与第二后端恢复仍按 SaaS 验收 分别验收。

取舍与验证

选择源站直达会公开源站地址，并需要独立维护证书。Cloudflare HTTP 代理、Worker 与 Tunnel 会收窄原契约；付费四层代理需要先取得协议、端口范围和报价证据。普通 Pod、共享 runner 与前缀权限不能证明恶意租户隔离。

Caddy 配置更新默认关闭 WebSocket，按入口维护处理，不承诺更新期间连接无损。负数刷新间隔会改变客户端断开时的取消行为，因此不用。Caddy 流式代理。

实际 HTTPS 验证覆盖登录与跨账户拒绝、静态鉴权、CLI 发布、WS/SSE、超过普通边缘阈值的请求及直传对象。有限时长测试证明配置行为，不证明无限连接或公网容量。证书、DNS、公开 TURN、生产身份、集群与迁移仍须在各自真实环境验收。
