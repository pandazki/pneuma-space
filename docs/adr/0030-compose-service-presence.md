# ADR 0030：Compose 上的平台服务，在网关的网络上且接受连接才算在

状态：**M2 决定**。取代 DESIGN 1.3 `rtc` 行"检查 `coturn` 服务名可解析"一句，以及 ADR 0010、ADR 0017 第 5 条"profile 未开时发布答 409"里按名字是否可解析判断 profile 的做法。2026-11-11 审查的 R10。

决定：

1. **在网络上，是名字解析到网关自己某个网络接口的子网里。** Compose 平面上网关只在平台网络上，Docker 的内置 DNS 对这个网络上的服务答这个网络里的地址；它不认识的名字转发给宿主的解析器，有的宿主对任何名字都答一个合成地址（假 IP 代理，常见 198.18.0.0/15）。所以答案不在网关自己的任何 IPv4 子网里（`os.networkInterfaces()`，回环除外），不论是谁答的，都是这个网络上没有这个服务。这是对答案的纯判断，不多一次 IO。解析照旧用有界的 `dns.Resolver`（500 ms，一次），不走 `getaddrinfo`（PR #4：libuv 的查询池会被一个答不上的名字堵住）。
2. **在，是在网络上并且接受连接。** 在网络上的地址在探测超时（1 s）内接受服务端口的 TCP 连接才算在。三种状态，含义不变：`off` 不在网络上（profile 没开），`down` 在网络上但不接受连接，`up` 接受连接。服务条显示这个判断；发布准入只在 `up` 时放行，两者出自同一个判断，不会不一致。不在时答的 409 和契约原有的一样（"start the platform with --profile …"）。
3. **runner 用同一条规则。** Compose 的 runner 池是一个固定地址，永远自称就绪，不能作数，所以 runner 按第 1、2 条在控制端口 8082 上判断。K8s 平面不变：runner 看池里就绪的 Pod，postgres 和 coturn 按 Service 名连接（Service 名没有 Pod 也可解析，本来就只能靠连接）。
4. **redis 也按第 1、2 条判断。** 它不在 profile 后面，不在网络上和不接受连接都是 `down`。
5. 探测有界，只在采样器里和发布时做；`GET /api/health`、`/api/metrics`、`/api/apps` 仍然零 IO。

理由：一个名字有 A 记录，只说明有解析器愿意答它，不说明服务在。Docker 内置 DNS 转发未知名字是它的正常行为，装了假 IP 代理的开发机并不少见；在那里，停掉的 runner 和 coturn 都"解析成功"，isolate 和 rtc 应用被接受发布，到唤醒时才失败（AC-ISO-5、AC-GAME-1）。子网判断把"谁答的"换成"答的地址在不在我所在的网络上"，网关自己的接口表就是这个网络的定义，不用另配。只看子网，会把刚停的容器留在缓存里的地址、或容器在而进程还没监听，当成在，所以准入还要连一次；发布本来就做 IO，多一次至多 1 s 的连接不改变它的量级。

拒绝：只连接不看子网（假 IP 代理通常先接受连接再去转发，连得上不证明是平台服务）；只看子网不连接（理由同上）；经 Docker API 查容器（Provider 和 Registry 不调 Docker，ADR 0017 第 2 条）；配置平台网络的网段（多一个要和 compose 保持一致的值，接口表已经是真相）；把 198.18.0.0/15 列入黑名单（各家代理用的网段不同）。

后果：发布一个需要 profile 服务的应用，多一次至多 1 s 的 TCP 连接。服务在网络上但还没开始监听（刚启动）时发布答 409，稍后重试即可。网关若接到第二个网络上，那个网络上同名的服务也算在；compose 只给网关一个网络。
