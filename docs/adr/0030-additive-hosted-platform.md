# 0030：SaaS 保留完整平台

状态：接受。2026-11-12。用户明确要求保留全部 M1、M2 应用能力和管理功能。

## 背景

[ADR 0027](0027-hosted-fetch-profile.md) 的独立 Fetch 入口只覆盖受限应用契约。实现又新建了精简控制台，既没有原有观测数据，也没有呈现已有的审计和版本历史。运行时实验因此被当成了完整 SaaS，违背用户要求。

## 决定

SaaS 使用现有 Node 网关、Registry、Store、Runtime、Provider、Scheduler、Metrics 和控制台。新增 `hosted` 身份模式，`local` 和 `upstream` 的语义不变。后端选择不能缩减 [M3 需求](../../REQUIREMENTS-M3.md) 的产品基线。Fetch 契约保留为独立实验，不替代契约 1。

托管登录由新的身份实现负责，先支持 GitHub。Registry 在同一平台库事务内登记不可变外部身份、用户、个人租户及管理员成员关系。已有身份不受新注册容量限制。Sessions 是登录握手、控制台会话、应用会话及一次性授权码的唯一写者。SQLite 与 PostgreSQL 使用同一组 Store 操作，不另建云端应用目录。

控制台和应用分别使用主机专属会话。应用登录经过绑定 AppId、精确源、父会话及浏览器随机值的一次性交换。退出使派生会话的下一次准入失效。控制台写入检查精确 Origin 和会话 CSRF 值。应用身份头、cookie 和 Bearer 凭据经过现有入口过滤，应用响应不能设置平台保留的 cookie。

新注册不授予平台管理员。运营者仍由 `PNEUMA_SPACE_PLATFORM_ADMINS` 指定。首次发布默认私有，现有应用的访问设置不迁改。令牌的到期时间、动作和 AppId 范围与原有权限取交集，旧令牌保持原权限。发布在激活前重新检查托管会话或令牌。管理、静态内容、动态请求、WebSocket 及触发入口使用同一授权规则。

完整平台继续提供原观测和运维视图。用户只看其权限内的应用和租户，平台管理员看全局。新增账户入口与凭据控制在原控制台实现，不再维护另一套完整产品界面。

## 验证与部署

新增行为和原功能回归由 [SaaS 验收](../acceptance.md#full-platform-saas) 定义。开发身份只能在明确的本地模式启用。正式托管登录需要身份提供者配置和独立的控制台、应用站点。

本决定改变登录方式，不改变已有运行时的信任承诺。完整能力在可信的本地环境及组织部署验证。面向不可信代码的公开注册还需要独立验证计算、网络、数据和控制面隔离。命名空间、网络策略和共享 runner 不能单独建立该保证。

## 取舍

选择在现有身份接缝增加实现，避免另一项服务与网关之间重复持有账户和授权状态。代价是网关增加登录和会话职责；这是对 M2 不实现登录的显式扩展，不改 M2 的部署模式。

Cloudflare 可承载适用的入口或存储服务。任何入口都必须通过原有流式请求、WebSocket、SSE、对象直传及 RTC 检查，不能用 Fetch 示例通过代替完整协议验证。
