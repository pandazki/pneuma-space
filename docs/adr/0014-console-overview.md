# ADR 0014：管理后台的平台总览

状态：**M1 决定**。用户 2026-11-05 提出"管理后台里面除了管理本身，监控看板是非常重要的"。

决定：管理后台在项目管理之外有一个总览页，指标从目标反推（`docs/user-stories.md` US-P-13）：平台服务可达性（G3：一条命令起平台，服务不在时发布和 KV 应用会失败）；App 和 Instance 按状态计数、awake 数对照 20 个的门槛、24 h 内被访问过的 App 数（G2：成本随运行数增长）；每个 awake 实例的 Lease 按 kind 计数（INV-3：回答"它为什么醒着"）；唤醒次数、失败数、冷启动中位数和 p95 对照 3 s 门槛（US-P-4）；每分钟请求和错误（US-P-6）；Delivery 的积压、进行中、失败和结果序列（INV-4 要求失败可见）；宿主机负载、内存、`/data` 所在文件系统余量、网关 RSS 和运行时长（G2 的 8 GB 机器）；最近 100 条生命周期事件（平台自身的失败要浮现）。

实现：一个 Metrics 组件只读内存，订阅生命周期事件流（原来各组件各自 `console.log` 的 JSON 行改为经一个事件函数输出，同时发给订阅者），每 10 s 采样 Stats 快照、实例和 Lease 计数、Delivery 计数、宿主机和服务探测；24 h 分钟桶；`GET /api/metrics` 返回一份快照，在请求路径上没有 Docker 和网络调用，所以 AC-P-8 的零 Docker 调用对它同样成立。列表接口加 `leases` 和 `since`，由 Runtime 的内存答复。后台是一个没有外部资源的 HTML 文件，内联 SVG 画图；中英双语，明暗主题。

拒绝：Prometheus 或 OpenTelemetry 端点（第二套系统和依赖，M1 的运营者只有一台机器和一个浏览器；M2 多节点时再评估）；把分钟桶写进平台库（M2 热力图用分时桶的行做这件事，到时总览改读库）；在 `/api/metrics` 里逐容器取 `docker stats`（请求路径上的 Docker 调用，M2 配额时作为采样器的一部分加入）；每应用的分时序列（内存随 App 数乘 1440 增长，属于 M2）。

后果：总览数据重启清零，页面注明采样起点。`REQUIREMENTS.md` 的"管理后台只做项目管理"改为"项目管理和平台观测"。
