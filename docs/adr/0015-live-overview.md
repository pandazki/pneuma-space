# ADR 0015：活的总览

状态：**M1 决定**。用户 2026-11-05 提出"dashboard 的动态性也太不够了……看看又实用又炫酷的管理后台可以怎么做"。

决定：总览以醒睡周期为主角，页面在打开期间是活的。浏览器在标签可见时每 2 s 轮询 `GET /api/metrics`、每 5 s 轮询 `GET /api/apps`，对比前后两份快照，差异驱动全部动效：并发位按实例状态点亮、呼吸、熄灭，对照 20 个的门槛；醒着的实例各一行状态时间线（唤醒及其耗时、醒着、排空、睡去），标注持有的 Lease、每秒请求和休眠时刻；三张分钟图上画出唤醒、失败、投递失败和发布的标记，共用一条十字线，当前分钟画成未完成并随轮询增长；失败进收件箱，可在浏览器本地标已读；事件流从顶部进入，悬停或上滚即暂停并计数新到达，页头写"直播中，上一条事件 N 秒前"；主机空闲时页面静止；尊重 `prefers-reduced-motion`。网关为此加两样内存数据：列表里每个醒着且没有 Lease 的实例带 `sleepsAt`（最后一次释放的时间加闲置秒数，由 Runtime 答复，持有 Lease 或未醒着时为 null）；每条生命周期事件带进程内递增的 `seq`，浏览器据此发现两次轮询之间 100 条环已溢出并报告缺口，而不是悄悄丢掉。

理由：G2 的意思是应用大多数时间在睡、醒得便宜、数量受上限约束，总览应该把这件事在发生时画出来。对 14 个运营者认可的后台的调研的共同点：活的东西是事件流；动效只标记转换中和新到达，稳态静止；实时有明确的暂停，页面明说"安静"不是"坏了"；事件画到图上，和尖峰共用时间轴。`/api/metrics` 只读内存且在 50 ms 内（AC-P-13），秒级轮询在契约之内。

拒绝：SSE 或 WebSocket 推流（admin 端口上的长连接和第二条数据路径，轮询已够；M2 多节点再评估）；10 s 粒度桶和主机负载序列（采样器和内存的改动，分钟桶加当前分钟的实时增长已能表达）；稳态上的跳数字和呼吸灯（不传递信息）；每个应用一个格子的地图作为总览（M1 里是一片不变的灰，放到项目页做视图）；日志跟随流（详情页按需重拉 `tail` 即可）。

后果：`GET /api/apps` 多一个字段，`/api/metrics` 的事件多一个字段，两者都来自内存，AC-P-8 和 AC-P-13 的零 Docker 调用不变。网关重启后 `seq` 从 1 重新开始，浏览器用 `gateway.startedAt` 识别重启。
