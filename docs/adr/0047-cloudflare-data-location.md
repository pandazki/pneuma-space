# ADR 0047：Cloudflare 承载面的数据放在请求进入的地方

状态：接受。2026-11-26。属于 [ADR 0041](0041-cloudflare-m1-plane.md) 的“一条命令安装”。

## 背景

请求在它进入的 Cloudflare 数据中心运行 Worker，Worker 从那里读写 D1 和 R2。D1 和 R2 不给提示时建在创建者附近，与请求从哪里进入无关。一个实测部署：从运营者的网络访问控制域名进入 SJC，访问 Cloudflare 自己的站点却进入 NRT；数据建在 APAC，每次打开应用的三个请求各有两次跨太平洋读 D1，占了平面耗时的大半。

应用自己的数据在它的 Durable Object 里。Durable Object 建在第一次访问它的 Worker 附近，之后不迁移；那个 Worker 就在创建请求进入的地方，所以它本来就跟着请求。容器不保证与 Durable Object 同地。

## 决定

1. **测量。** 首次安装先把占位 Worker 部署到 Worker 名下并挂上控制域名，从安装机器请求 `/cdn-cgi/trace` 读 `colo`（HTTPS 尚未就绪时读 `CF-Ray` 的后缀），再创建数据。必须走部署自己的 zone：同一网络到不同 zone 的任播地址可能进入不同的数据中心。随后真正的部署覆盖占位 Worker。
2. **换算。** 数据中心按 `cf/scripts/colo-locations.json` 换成 D1/R2 的位置提示（`wnam`、`enam`、`weur`、`eeur`、`apac`、`oc`），表由 `colo-locations.mjs` 按到各提示锚点的最近距离生成。
3. **选择。** `--location` 优先。测不到或数据中心不在表里就停下让运营者选，不用默认。位置、Cloudflare 报告的实际位置和进入的数据中心写进 `data.json`，每次结束时打印。重跑发现数据与进入点不在一处，只用一行说明并给出搬迁命令，不搬。
4. **搬迁。** `--relocate HINT` 先只打印计划和不能自动保证的事项，加 `--yes` 才执行。新资源名为 `PREFIX-HINT`、`PREFIX-HINT-artifacts`、`PREFIX-HINT-objects`：名字在账户内唯一，而 R2 删除后重建同名桶沿用原位置，名字带上位置就既不冲突也不错位。复制和校验都在 Worker 仍用旧数据时进行，新资源这时没有任何写入方：新库先清空审计表以外的表再写入，审计表用 `INSERT OR IGNORE`，中断后重跑不重复；新桶对照旧桶补齐、删多余。校验每表行数和摘要、审计触发器、对象的键/大小/ETag、每个制品的 SHA-256，全部一致后才把新名字记为当前，再写 Worker 配置（数据库 ID、两个桶的绑定和签名用的桶名变量）并重新部署。R2 签名密钥来自同一个账户令牌，复制本身就用这把密钥，复制成功即说明 Worker 能为新桶签名。部署成功后追加复制之后写进旧库的审计行，以及最后一次同步之后才写进旧桶、新桶没有的对象。
5. **删除旧资源。** 旧库和旧桶保留，直到运营者运行 `--remove-previous`。它要求切换已过一小时（`signR2` 签名最长一小时），已部署的 Worker 只绑定新数据，再追加一次，并确认旧审计行都已在新库，才清空、删除旧桶和旧库。
6. **不搬 Durable Object 和容器。**

## 后果

- 测量代表安装机器的网络路径。用户主要从别处进入时，运营者要用 `--location`。位置提示尽力而为，搬迁时新资源不在所提示的位置就在复制前停下。
- 复制之后、切换之前的发布、建删应用、账户、令牌、邀请、登录和请求计数不进新库，审计除外；搬迁前要停下这些操作，计划里写明。切换前签发的地址：下载在删除旧桶之前可用；上传若在切换后才完成，完成会失败，要重传，事后的追加可能留下一个没有引用的对象。
- 重新部署照常重启应用。R2 字节经安装机器转发（GET 后 PUT），适合小部署。
- 不做：D1 读副本、Smart Placement、自动搬迁。
