# ADR 0051：Cloudflare 承载面只有应用自己的失败计入隔离

状态：接受。2026-11-27。补充 [CF 应用契约](../../cf/docs/app-contract.md)：唤醒被运行名额拒绝时的答复，以及失败计数计什么、何时清零。后果中“分界靠就绪检查的采样”一条由 [ADR 0053](0053-cloudflare-runner-reports-app-exit.md) 取代。

## 背景

这个平台要承载很多同一形态的应用，每个都活好几年、很少被打开。所以大多数应用在休眠，一个空间的运行名额（`awake`，默认 2）有意设得小。对这样的应用，打开时被拒绝一个名额是正常、预料中的事。

`Runtime.acquire` 把预留名额和启动容器放在同一个 `try` 里。名额满时 `reserveCompute` 以 503 `compute_quota` 拒绝，`catch` 却把它当成启动失败：失败计数加一，记一条 `wake-failed`，`retire(true)`。到 `maxFailures`（默认 5）次就把应用隔离，此后每个请求都答 503 `quarantined`，空出名额也一样，直到有人解除。成功的唤醒也不清零计数。

2026-11-27 在真实部署上：空间里另有两个应用醒着，两个长期应用各被一个遇 503 每 15 s 重试的客户端打开，各被拒绝 5 次后都被隔离，失败计数为 5，每条 `wake-failed` 都是“Startup failed: The space has reached its running application limit.”。第三个应用只被打开一次，也记了一次失败（issue #67）。

另两个承载面的契约早已说清同一情形：名额满时，会唤醒应用的请求得到 503 和 `Retry-After: 30`，不算失败；这样被拒绝的触发投递 30 s 后重试，不用掉一次尝试（[ADR 0023](0023-quotas.md) 第 5 条）。

## 决定

隔离是一个断路器：同一个发布一再起不来时，停止徒劳的冷启动（每次占一个名额，最长 45 s），并让拥有者看到它坏了；恢复要人来做，发布或 `unquarantine`。所以计数只收“这个发布的代码跑不起来”的证据。

1. **名额不足的拒绝不是一次唤醒。** 答 503 `compute_quota`，带 `Retry-After: 30`。不记唤醒，运行状态和上一次唤醒记录恢复原样，不计失败，不退役。名额一空出来，下一个请求就唤醒应用。`Retry-After` 由错误本身携带，经应用单元和控制面 API 原样传出，所以控制台的唤醒动作和发布遇到满空间时也带它。
2. **只有应用自己的进程失败才计数。** 计入的有两种：运行器报告已解开发布之后，应用进程在期限内没有就绪（退出或没有监听）；一个醒着的实例不再回应就绪检查。在运行器解开发布之前的失败都是平台的：预留名额的其它错误、服务绑定、容器启动、运行器没有回应、取包和解包。它们仍记一条失败的唤醒供诊断，但不计数。分界用唤醒记录里已有的 `unpack` 阶段：它有值，应用代码就已经开始运行。
3. **成功的唤醒清零。** 计数的含义是“自上次成功唤醒以来连续失败的次数”。一次成功说明这个发布起得来，之前的失败是暂时的。几个月里零星、互不相关的失败不会累积成隔离。
4. **触发投递遇到满空间，30 s 后重试，不用一次尝试。** 平台的拒绝没有到达触发器。规则同契约 1。
5. **失败的发布不把候选发布的失败记到旧发布上。** 回滚时恢复旧发布原来的计数。此前 `maxFailures` 为 1 时，一次起不来的发布会把仍能工作的旧发布隔离。
6. **不变的部分。** `maxFailures` 默认 5，可按应用调整；隔离后需要 Node 的请求答 503 `quarantined`，直到发布或 `unquarantine`；静态文件照旧由 Worker 返回。

## 被拒绝的方案

- **只在 `catch` 里放过 `compute_quota`，其余照旧计数。** 平台出故障、容器起不来时，空间里每个被打开的应用都会被隔离，又要逐个人工解除，正是这个缺陷换个原因再来一次。
- **像契约 1 那样用时间窗（默认 60 s）代替清零。** 这里一次失败的唤醒最长 45 s，60 s 的窗装不下 5 次失败，应用永远不会被隔离；窗若放宽到装得下，又会重新累积零星的失败。连续计数不依赖时间，直接表达“这个发布起不来”。
- **不再计醒着的实例就绪检查失败。** 成功唤醒清零之后，这一次只在紧接着的唤醒也失败时才有分量；保留现状，少改一处。
- **被拒绝的请求退还每日请求额度。** 额度计的是到达平台的请求，不论答复：静态文件和其它拒绝同样计。一个被服务的请求也花一个额度，拒绝没有多收；遵守 `Retry-After` 的客户端一小时至多 120 次。
- **先预留名额再写下启动中的状态。** 写下 `bootId` 在先，是为了应用单元在预留之后崩溃时能凭它释放名额；预留在先会留下应用自己清不掉的名额行。

## 后果

- 空间满时被打开的应用只得到 503 和 `Retry-After`，计数、唤醒记录和事件都不变。
- 平台故障造成的失败唤醒仍出现在事件里，但不会把应用隔离；平台恢复后应用自己就能起来。
- 分界靠就绪检查的采样：应用若在两次检查之间就退出、运行器随即停止回应，这次唤醒看不到 `unpack`，按平台的失败记录、不计数。宁可漏计，不错计：漏计的代价是一次徒劳的唤醒，错计会隔离一个能工作的应用。
- 一个起得来、随后在请求中崩溃的应用不会被隔离：每次重新唤醒都成功并清零。每次唤醒都由请求引起，受每日请求额度约束。
- 等待名额的触发投递每次重试都计一次每日请求，与其它请求相同。
- 已经被这个缺陷隔离的应用不会自动恢复，仍需 `unquarantine` 或重新发布。
