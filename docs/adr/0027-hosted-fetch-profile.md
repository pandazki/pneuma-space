# 0027：独立云入口与可迁移的 Fetch 契约

状态：接受。2026-11-11。

## 背景

用户要求自助注册、个人私有空间和可撤销的程序凭据。首个后端选 Cloudflare，允许现有应用适配受限运行时，保留将来迁往其他云的能力。

[ADR 0012](0012-implementation-stack.md) 的 Node 网关处理进程、TCP、文件挂载和平台数据库会话。[ADR 0017](0017-pluggable-runtimes.md) 的运行时接缝不能使这些实现直接运行在 Worker 内。把托管调用伪装成有地址、可休眠的进程，会使租约、计量和存储承诺失真。

## 决定

新增 `cloud/` 入口和显式的应用契约 2。M1、M2 的契约 1、Node 网关和部署方式保留。共享名称、错误和能力目录等实际共用的纯定义，不抽取现有进程编排。新的产品范围在 [M3 需求](../../REQUIREMENTS-M3.md)，模型和唯一写者在 [DESIGN](../../DESIGN.md#5-m3-云入口)，应用接口在 [应用契约](../app-contract.md#cloud-profile-contract-2)。

云应用导出 Web Fetch 处理函数。只有 `FetchRuntime.acquire` 能取得应用调用权，返回有期限的 Fetch 调用对象。它不产生 TCP 地址、常驻实例、唤醒次数或虚构的运行时长。`prepare` 只做有资源上限且无应用数据权限的模块检查。正常请求在入口 Worker 调用，检查可以在当前租户的一次发布命令中调用。

首个计算适配器选择 [Dynamic Workers](https://developers.cloudflare.com/dynamic-workers/)。不可变制品及固定运行配置共同决定加载键，键含 AppId。每次请求的身份、数据权限和期限通过请求参数传递，绝不写入被缓存的运行配置。网络默认拒绝，运行环境不注入平台凭据或命名空间。

[Worker Loader](https://developers.cloudflare.com/dynamic-workers/api-reference/) 可以按不可变键加载存储中的代码。日常发布因此不需要 Cloudflare 账户管理令牌或逐个创建远端脚本。实际账户、付费计划与边界行为仍须实测。本地 workerd 验证只证明本地引擎行为。

基础设施端口按其承诺拆分为身份认证、账户目录、租户存储、制品存储、计算执行和能力资源。业务代码与应用 ABI 不导入云厂商类型。Cloudflare 适配器使用 Worker、SQLite Durable Objects 和 R2。第二套本地适配器使用 SQLite 与文件存储，运行同一可信示例并恢复导出数据。它证明契约与数据可迁移，不证明 AWS 的生产隔离。AWS 适配器须另行满足相同验收，不预先实现空壳。

新增 `records` 能力及其 Provider。它提供有版本条件的 JSON 记录，不冒充 SQL、Redis 或文件系统。Provider 保持 `ensure`、`inject`、`suspend`、`destroy`，不知道运行时或部署平面。契约 1 不接受这个能力。目录按契约派生支持范围，不复制两套支持清单。

## 并发与恢复的取舍

租户内命令先持久化操作意图，再执行外部效果，最后按命令序号条件提交。每个应用最多一个待完成发布；不同幂等键的并发发布得到冲突。下线使更早的发布失去提交资格。这个行为只适用于契约 2，不改 AC-STORE-2。

首版通过同一幂等键的重试恢复中断的发布。待完成和失败状态可见，不以 `waitUntil` 充当持久任务。下线与清除可重复完成其未完成阶段。暂不加入通用后台工作流或账户管理 API 供应任务。

## 被拒绝的方案

- 直接把现有网关放进 Cloudflare Containers。其默认磁盘是临时的，不能兑现 `/data`，仍要另外解决数据库会话和长驻进程。
- 为现有 Runtime、Store 的每个进程方法补空实现。类型相同不能建立语义兼容。
- 首版同时实现 Workers for Platforms 和 Dynamic Workers。前者需要额外的脚本供应、凭据和清理；只在所选适配器实际无法满足要求时重新决定。
- 先公开任意 SQL 或原生数据库绑定。首版无法据此准确限制记录操作、导出语义和旧权限的有效期。
- 用厂商 SDK 作为应用契约。迁移会要求修改每个应用。

## 后果

这个阶段不承诺契约 1 应用无修改迁入云端。新平台模型仍只认识开发者、租户、应用、版本、凭据和资源。外部开发工具不成为平台实体。M3 的其他能力在明确契约和验收后增加。
