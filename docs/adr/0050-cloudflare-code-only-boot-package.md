# ADR 0050：Cloudflare 承载面唤醒时只取代码

状态：接受。2026-11-27。修订 [CF 应用契约](../../cf/docs/app-contract.md) 中“唤醒时从 R2 重建代码”：重建的是静态目录以外的文件。

## 背景

打开一个休眠的 Node 应用，要等运行器取包、解包、应用开始监听。运行器取回的是整个包：一份 JSON，每个文件一段 base64，静态目录也在里面。它校验散列、解析、逐个写盘，然后才启动应用。静态目录的文件由 Worker 在授权后从 R2 返回（[ADR 0045](0045-cloudflare-first-screen-and-idle.md)），Node 进程用不到它们。

2026-11-27 在真实部署上实测：同一个 Node 应用，静态部分大小不同，四档轮流，每档 8 次请求唤醒，全部成功。取包加解包的中位数在包为 0.03 MiB 时 135 ms，1.0 MiB 时 195 ms，2.4 MiB 时 339 ms，3.9 MiB 时 392 ms，约每 MiB 包 70 ms。客户端用时同步增长，从 1339 ms 到 1598 ms。解包在容器的 `lite` 实例上用 167 ms，同一个包在开发机上用 25 ms，所以解包受容器的 CPU 限制（推断）。打开应用最要紧的是快，静态文件却让每次唤醒多付这段时间，而且随应用的图片、字体变大而变大。

## 决定

1. **发布时另写一个代码包。** 声明了 `static` 的 Node 应用从上传发布时，平台在整个包旁边写一个代码包：格式相同，含静态目录以外的全部文件，按它自己的 SHA-256 命名。发布记录用 `code` 记下它的键和摘要。
2. **唤醒时只取代码包。** 应用单元把代码包交给运行器，并用它的摘要启动容器，运行器照旧校验摘要。没有 `code` 的发布照旧取整个包，包括本决定之前的发布、回滚到这些发布，以及没有声明 `static` 的 Node 应用。运行器和镜像都不变。
3. **容器里没有静态目录的文件。** 应用不能从磁盘读取它们，运行时要读的文件放在静态目录之外。入口在静态目录里的上传，在开始上传时就以 400 `entry` 拒绝。

## 被拒绝的方案

- **照旧取整个包，只是不写静态文件。** 取包仍随大小增长，解包仍要校验和解析整个包。
- **唤醒时由应用单元从整个包里滤出代码。** 每次唤醒都要在 Durable Object 里读出并解析最多 4 MiB，发布时做一次的事变成每次打开都做。
- **先启动应用，再在后台写静态文件。** 取包仍随大小增长；应用启动初期读到的目录不完整，契约说不清。
- **代码包用固定键。** 同一个上传在平台改变编码后再发布，会遇到旧对象，摘要对不上，启动失败。

## 后果

- 唤醒用时不再随静态目录增长，发布后的测量见 [验证记录](../../cf/docs/verification.md)。
- 已有的发布要等重新发布才得到代码包，在那之前照旧取整个包，用时不变。
- 每个带静态目录的 Node 发布多一个 R2 对象。代码包加解码后的静态文件约为一个包的大小，仍在每张上传票据预留的三倍之内，清除应用时随应用前缀一起删除。
- 从磁盘读取静态目录文件的 Node 应用，下次发布后会读不到它们。仓库里的起步模板和 notebook 示例、agent-app-governance 的模板，以及作者机器上找到的 7 个 CF Node 应用，服务端代码都不读文件。
- 入口在静态目录里的新上传被拒绝。已有的这种发布照旧取整个包，也可以回滚到它。
