# ADR 0016：实时页与请求记录

状态：**M1 决定**。用户 2026-11-05 提出"做一个有点像 realtime 的专门的 tab，展示更实时的访问信息，可以展开更详细信息，同时 Event tail 和报错这些都流式滚动……顶部支持过滤器"，并要求总览的醒着实例时间线最多画最近 10 个。

决定：后台加第三个页面"实时"。网关内存里加一个请求记录环，最近 1000 条。Ingress 在响应结束时写一条（静态直出也记，类别 static；WebSocket 在关闭时写一条，类别 ws，耗时是连接存续时间），Scheduler 在每次投递尝试结束时写一条（类别 trigger）。字段：进程内递增的 seq、结束时间 t、应用、类别（request、static、ws、trigger）、方法、路径（不含查询串，截到 200 字符）、状态码、总耗时、等上游就绪的时间（含唤醒）、是否冷启动（acquire 前实例不是 awake）、主体、错误文本。`GET /api/requests?after=<seq>&limit=<n>` 只读内存，返回序号大于 after 的记录，默认最多 500 条，请求路径上没有 Docker 和网络调用。实时页在标签可见时每 1 s 以游标轮询它，事件流同页用 `/api/metrics` 的事件环；两条流同一套跟随规则（ADR 0015：悬停或上滚即暂停并计数新到达，序号缺口显示为缺口行）；一行可展开看全部字段；顶部一个过滤框，语法 `app:<name> kind:<kind> status:<code|2xx..5xx> path:<substring> subject:<substring> cold:true error:true`，加"只看错误"和"隐藏静态"两个开关，过滤同时作用于请求流和事件流，并写进 URL 的查询串。总览的醒着实例时间线只画最近有变化的 10 个应用。

理由：总览回答"平台在发生什么"，实时页回答"此刻是谁在访问、快不快、有没有唤醒、有没有错"，这是浏览器 Network 面板和 Live Tail 的形状，运营者已经熟悉。逐请求记录只有放在内存里才能既做到秒级又不违反 AC-P-8 和 AC-P-13（不写库，不碰 Docker）。1000 条约 300 KB，内存有界（G2）。游标轮询比推流省一条长连接，和 ADR 0015 一致。

拒绝：把请求记录写进平台库或日志文件（M2 的访问日志再议，那时要有保留期和体积上限）；记录请求头和查询串（可能带令牌，路径和主体已够用）；记录字节数（keep-alive 下 socket 计数只是近似，不给近似数）；按请求推流（同 ADR 0015）；用这页替代应用自己的日志（详情页的容器日志仍是应用输出的入口）。

后果：Ingress 和 Scheduler 多一个只写内存的调用；admin API 多一个端点；后台多一个入口；重启清零，seq 从 1 重新开始。
