# ADR 0041：Cloudflare 是 M1 的第二个承载面

状态：接受。2026-11-24。用户确认这项工作属于 M1，与本机 Docker 平行，并确认以下各项。修订 [ADR 0033](0033-hosted-fetch-profile.md)（Fetch 实验退出）和 G4 对层次的描述。

## 背景

用户提出一条新故事：我有自己的 Cloudflare 账户，在上面搭一个只给自己用的应用中心，以后让自己的开发工具往里新增、修改、下架应用；工具只凭这个中心的地址就能取得说明和授权，不带之前的上下文也能继续维护。

仓库里和 Cloudflare 有关的东西有三样，都不是为这条故事做的：

| 实现 | 当初回答的问题 | 应用契约 |
| --- | --- | --- |
| `cloud/` | M3 公开 SaaS 的受限首版（ADR 0033） | 契约 2 |
| `deploy/hosted` | SaaS 保留完整平台（[ADR 0036](0036-additive-hosted-platform.md)） | 契约 1 |
| 未公开的独立 Cloudflare 版 | 一个邀请制多租户站点 | 自己的原生接口 |

2026-11-24 让一个只看得到公开材料的开发者在自有账户上实测：`cloud/` 走不通，它要求控制台和应用属于不同的可注册域名；独立 Cloudflare 版走通，代价是一次人工建令牌、三次部署和一次重发。走通说明它能用于这条故事，不说明它是为此设计的。

原样把它并入会留下三个问题：

- 应用契约成了三套，同一个应用不能在两种承载面上运行，清单、命令行和模板各不相同。这和 G1、G14 相反。
- 故事的后两半（程序化地增改下架、中心自己提供说明和授权）与 Cloudflare 无关，本机和集群部署同样需要，今天同样没有。
- 临时应用（[ADR 0038](0038-ephemeral-apps.md)）和受管应用（[ADR 0039](0039-managed-apps.md)）只在 Node 网关上有，建在它们之上的程序接不上 Cloudflare 版。

## 决定

1. **定位。** Cloudflare 版属于 M1，是与本机 Docker 平行的第二个承载面：一个可信的拥有者，可信的应用代码，信任边界同 [M1](../../REQUIREMENTS.md#信任边界)，承载从一台 Docker 机器换成一个 Cloudflare 账户。它不是 M3 的实现；M3 仍按 ADR 0036。它已有的租户、邀请和分角色控制台保留，不作为对不可信租户的隔离承诺，也不再扩展。
2. **契约两套，开发者表面一套。** 契约 1 的 PostgreSQL、Redis 协议和挂载卷在 Cloudflare 上无法兑现，所以底层接口保持两套：契约 1 和 Cloudflare 原生契约。命令行的动词、清单文件名、模板结构、中心自述和授权协议只定义一次，每个承载面各自实现。同一个应用跨承载面运行不在本决定内，要做时另写 ADR。
3. **中心自述和授权与承载面无关。** 平台提供两样东西：一个固定地址，返回这个部署的入口、契约版本和取得凭据的方法；一个设备授权流程，程序发起、拥有者在已登录的控制台批准、程序得到有范围和期限的凭据。凭据可以发布、移除和恢复自己范围内的应用，不能清除，不能管理账户。Cloudflare 承载面先实现，本机和集群随后。面向编码工具的说明和技能只在 `templates/` 里，平台模型不出现它们。
4. **`cloud/` 退出。** Fetch 实验既不服务 M3（ADR 0036 已否定），也不服务这条故事。删除 `cloud/`、契约 2、`records` 能力和它们的文档与示例。
5. **安装。** 运营者给出域名和资源前缀，一条命令完成安装。Cloudflare 的登录授权建不了运行时需要的长期令牌，所以保留一个人工步骤：打开预填权限的建令牌链接，把令牌交给安装命令。安装可重入，中断后再跑同一条命令续上。仓库不带任何具体部署的域名、账户或资源标识。
6. **补齐。** 临时应用和受管应用在 Cloudflare 承载面按原语义实现，之后才称这个承载面完整。

## 顺序

本 ADR 和故事 → Cloudflare 版进主干并删除 `cloud/` → 一条命令安装 → 自述、授权、移除与恢复 → 临时应用和受管应用 → 评估不起容器的运行方式。每一步以真实账户上的验证收尾。

## 被拒绝的方案

- **原样并入，照旧各做各的。** 最快，但把三套契约和两套命令行定为正式，后两半故事只在 Cloudflare 上有。
- **把 Cloudflare 版当作 M3。** ADR 0036 要求 SaaS 保留契约 1 的全部能力，它不满足；它也没有做过对抗性租户的隔离验收。
- **先统一成一套应用接口再并入。** 要给 Node 网关也实现一套原生接口并迁移全部示例，这条故事不需要它。
- **只为单个拥有者重写一版更小的。** 现有实现已通过实测，多出来的部分不妨碍这条故事。

## 后果

- 仓库同时有两套应用契约，文档要在入口处说清各自对应哪个承载面。
- G14 的“第二套适配器恢复”失去 `cloud/` 里的那份本地适配器证明，M3 的这个目标回到未验证。
- Cloudflare 版的源码此前按用户要求不公开，并入主干即公开，不可撤回。
- 每个应用一个 Container，不是 isolate；每个应用一个精确域名，首次发布要等证书。两者是这个承载面当前的成本，在“顺序”最后一步重新评估。
