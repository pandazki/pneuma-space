# ADR 0024：观测落库、热力图、审计、指标、节点与日志

状态：**M2 决定**。取代 ADR 0014、0015、0016 里"M2 再议"的部分。设计探索稿 M2-D4 第 2 到 8 节。

决定：

1. **热力图是一张 `usage` 表**，Metrics 现有的分钟桶就是它的行。列：`app`（App id，`'*'` 表示整个平台）、`tenant`（写入时的租户，App 之后移租户历史留在原租户，M3 计量按此计）、`step`（60 或 3600 秒）、`start`、`replica`、`requests`、`errors`、`wakes`、`wake_failures`、`sleeps`、`deliveries_done`、`deliveries_failed`、`deliveries_retried`、`wake_ms`（成功唤醒耗时之和）、`awake_ms`。主键 `(app, step, start, replica)`，索引 `(tenant, step, start)`。哪些行存在：每个应用的 3600 步长行；`'*'` 的 60 和 3600 步长行。没有每应用的分钟行。
2. **每副本只写自己的行，读时求和。** 副本在内存里累计当前桶，采样器每 10 s 把本副本本桶的绝对值以 `INSERT ... ON CONFLICT DO UPDATE SET col = excluded.col` 写入：没有共享写目标所以没有锁，写绝对值所以重试幂等，副本崩溃最多丢 10 s。`replica` 列是 `<副本名>@<启动毫秒>`：重启后的副本名字没变但内存清零，它的第一次写不能覆盖同一小时里重启前的计数，代价是每次重启每个桶多一行。`awake_ms` 只由领导者在每次采样时按实例行累加，精度 10 s。保留期是全局专用 Policy 字段 `usage_retention_days`（默认 90），领导者每小时删 `step = 3600` 且早于保留期的行、`step = 60` 且早于 24 h 的行。
3. **谁读。** 总览的 `series` 改读 `'*'` 的 60 步长行按 `start` 对副本求和；`wakeP50Ms` 换成 `wakeMeanMs = wake_ms / wakes`（均值能跨副本合并，分位数不能）；`wakes.last1h/last24h` 的 p50 和 p95 由采样器每 60 s 从 `events` 表的 `awake` 事件算出；读都在采样器里做，`snapshot()` 仍只读内存（AC-P-13 不变）。总览新增热度格：`'*'` 的 3600 步长行近 30 天，行是星期几、列是小时。项目页 `GET /api/usage?app=&from=&to=` 返回该应用的 3600 步长序列画成天乘小时的格子；团队页 `GET /api/usage?tenant=`；排行 `GET /api/usage/apps?from=&to=&tenant=&limit=50`。"一个月没人碰"用列表已有的 `lastAccessAt`。`stats` 表只剩 `(app, last_access_at)`，写法 `max(旧, 新)`；列表的 `requests`、`errors` 改为近 24 h，取自 `usage`，由采样器缓存进内存。
4. **事件落库。** 生命周期事件（含 `delivery.*` 的投递结果和原因）写 `events(id, at, replica, ev, app, tenant, body)`，`at` 取库时钟，同时照旧写 stdout 一行 JSON。副本每 1 s 或每 100 条批量插入。保留由全局专用 Policy `events_retention_days`（14）和 `events_max_rows`（1 000 000）决定，领导者每小时先按时间删再按行数删最旧的。`/api/metrics` 的 `events` 和收件箱读库；`seq` 改为 `id`，全局递增，不随重启归零；游标返回 `id > after` 且 `at < 库时钟 - 2 s` 的行，2 s 的沉淀期覆盖并发事务按 id 乱序提交，事件尾晚 2 s 出现但不漏行。`done`、`cancelled` 且早于 `events_retention_days` 的 Delivery 行由同一次清扫删除，`failed` 留到 purge（INV-4）。
5. **请求记录不进库。** 每条一行 JSON 写 stdout，进集群日志（单机是 Docker 日志驱动，compose 给网关设 `max-size` 和 `max-file`）；内存环 1000 条照旧。实时页的 `GET /api/requests` 由接到请求的副本扇出：对 `PNEUMA_SPACE_PEERS`（无头 Service 的 DNS 名）解析出的每个副本发 `GET /api/requests?local=1&after=<该副本的 seq>`，转发调用者自己的凭据头，按 `t` 归并；游标变成不透明串 `<replica>:<seq>,...`，记录带 `replica`，某副本不可达时响应里标出它，页面显示缺口行。未设 `PNEUMA_SPACE_PEERS` 即单副本，不扇出。控制台不读集群日志：平台库和副本内存是它的全部数据源。
6. **审计表 `audit(id, at, actor, actor_tenant, tenant, action, target_kind, target, result, details)`。** `actor` 是主体串，`actor_tenant` 是此次行使权限所在的租户（平台管理员为空），`tenant` 是被操作对象的租户；`target_kind` 为 `app | tenant | token | member | policy`；`result` 为 `ok | refused | error`；`details` 是不含密钥的 JSON（Release 号和 `release_key`、策略补丁、配额补丁、令牌 id、错误文本）。只追加由结构保证：迁移建 `BEFORE UPDATE OR DELETE` 触发器直接报错，没有任何 API 能改或删，M2 不清理审计行。写者是管理边界：路由表的每个变更路由声明 `audit: {action, target}`，分发器在处理函数之前写一行 `result = started`，结束后再写一行结果，成功、拒绝、出错都写；网关在命令中途被滚动重启，审计里留下的是一行 `started`，而不是什么都没有。动作：`app.publish`、`app.remove`、`app.purge`、`app.policy`、`app.owner`、`app.access`、`app.move`、`app.unquarantine`、`policy.global`、`token.issue`、`token.revoke`、`tenant.create`、`tenant.quota`、`member.add`、`member.role`、`member.remove`。查询 `GET /api/audit?tenant=&from=&to=&actor=&action=&target=&limit=`（租户成员只能查本租户），`appctl audit [--tenant t] [--since 7d] [--action app.purge] [--json]` 默认打印 TSV。不做控制台页。
7. **指标端点 `GET /metrics`**，Prometheus 文本格式，`metrics.ts` 里字符串拼接，不用库。开在单独端口 `PNEUMA_SPACE_METRICS_PORT`，未设即不开，compose 默认不开；K8s 下由 NetworkPolicy 只放行组织的监控命名空间。序列：每副本导出 `pneuma_space_requests_total{tenant,runtime,kind}`、`pneuma_space_errors_total{tenant,runtime}`、`pneuma_space_wakes_total{tenant,runtime,result}`、`pneuma_space_wake_duration_seconds{runtime}`（直方图，桶 0.05 0.1 0.25 0.5 1 2 5 15）、`pneuma_space_events_total{ev}`、网关的常驻内存和启动时间；只有领导者导出 `pneuma_space_instances{state,runtime,tenant}`、`pneuma_space_tenant_quota_used/limit{tenant,resource}`、`pneuma_space_deliveries{state}`、`pneuma_space_service_up{service}`，否则会被求和成 N 倍。没有带 `app` 标签的序列：每应用的热度在 `usage` 表和控制台里，基数因此只随租户数增长。
8. **节点视图 `GET /api/nodes`** 读采样器的缓存，请求路径上没有 K8s 调用。采样器每 15 s 经 `Infra.nodes()`（K8s 平面读 `nodes` 的 allocatable、Ready、`unschedulable`、污点、标签，以及两个平台命名空间里带 `pneuma-space.role` 标签的 Pod 的 `nodeName`、`requests`、阶段、就绪和重启次数；RBAC 只需集群级只读 `nodes` 和已有的 Pod 读权限）采一次，没有人看时也只是这一个列表调用；`requested` 是平台自己的 Pod 之和，不是节点上全部 Pod，不读 `metrics.k8s.io`。isolate 实例的节点取自它所在 runner 的节点，runner 健康来自 IsolateRuntime 已有的查询。形状 `{source: 'k8s' | 'host', nodes: [{name, ready, schedulable, labels, allocatable, requested, used | null, gateways, runner | null, instances: [{app, runtime, state}]}]}`，`AppSummary` 加 `node`。单机退化为 `source: 'host'`，一个节点，`hostSample()` 原样复用；总览的主机卡在 K8s 下换成集群卡（就绪节点数，已请求对 allocatable 的 CPU 和内存）。拓扑页的切换从两个视图变三个，加"节点"：每个节点一个框，框头是名字、就绪、可调度、CPU 和内存条，框里是该节点的网关、runner 和应用芯片，沿用泳道的 12 个上限和 +N；泳道的应用芯片带节点名小字。
9. **日志。** container 的实例日志就是 Pod 日志，任一副本经 K8s API 取；删 Pod 前取尾部 200 行（上限 64 KiB）存 `instance_log(app, release, ended_at, reason, tail)`，每 App 一行覆盖写，没有活 Pod 时 `logs()` 返回它。isolate 任一副本问实例所在的 runner，接口不变；runner 另把每条 worker 行以 `{t, app, release, stream, line}` 写自己的 stdout 进集群日志。控制台日志尾巴照旧按需重拉，不做跟随流（ADR 0015）。
10. **状态清单。** `GET /api/apps/<name>/state` 和 `GET /api/state?tenant=`，`appctl state <name> [--json]`：每条 Binding 一项 `{kind, provider, state, location}`，`location` 是 Provider 私有 `resource` 去掉凭据后的部分（PVC 名、命名空间和存储类，单机是卷名；PostgreSQL 的服务地址和库名；kv 的服务地址和前缀；object 的端点和 bucket），另列 Release 的 bundle id。每种后端的常规备份怎么做写进运营文档，由存储层做。不做导出和恢复（`REQUIREMENTS-M2.md` 备份行）。
11. **新增全局专用 Policy 字段**（不进 `PolicyOverride`，和 `timezone` 一样）：`usage_retention_days=90`、`events_retention_days=14`、`events_max_rows=1000000`，经 `appctl policy` 修改，所以被审计。环境变量：`PNEUMA_SPACE_REPLICA`、`PNEUMA_SPACE_PEERS`、`PNEUMA_SPACE_METRICS_PORT`、`PNEUMA_SPACE_CPU_REQUEST_MILLIS`。

理由：按副本分行写绝对值没有锁也不会重复计数，行数只多一个小倍数，冷应用只出现在一个副本的行里。每应用分钟桶会让行数在保留期内乘 60，只用小时步长会丢掉总览的实时分钟图（ADR 0015），所以两种步长。请求记录是请求量级的写，平台库同时承载唤醒认领的锁，历史交给集群日志、此刻的视图靠扇出。审计写在管理边界而不是 Registry 命令里，Registry 的命令就不用穿一个 actor 参数，而且令牌和成员的命令不全归 Registry。`appctl audit` 比控制台页小一个数量级，US-O-6 一条命令就答。`/metrics` 不放管理口，否则只能给 Prometheus 一枚有写权限的管理令牌。

拒绝：加法 UPSERT（失败重试重复计数）；每应用分钟桶或只用一种步长；请求记录写平台库；事件和请求经 SSE 或 LISTEN 推送（ADR 0015 的理由）；审计写在 Registry 的命令事务里；审计控制台页；`/metrics` 放管理口要令牌；导出和恢复命令（要给 Provider 加 `export`、`import` 两个动作，只能在 `removed` 时做即停服，Redis 数据导不出来）。

后果：`awake_ms` 精度 10 s 且依赖领导者连续运行，切换领导时丢一个采样间隔，M3 若按在跑时长计费要改成按状态转换精确计。事件尾晚 2 s；库变慢到批量插入超过 2 s 时事件尾可能漏行，漏掉的行仍在库里。扇出依赖无头 Service 和可转发的凭据头（JWT 和平台令牌都是请求头，可转发）。命令中途崩溃时审计只有 `started` 一行，没有结果行。`/metrics` 的开放端口只靠 NetworkPolicy 收口，集群不支持 NetworkPolicy 就不开它。全集群 Running Pod 列表在大集群上是几千个对象，懒采样加 15 s 缓存控制频率，没量过。事件 `seq` 变 `id`，控制台游标随之改。
