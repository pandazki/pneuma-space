# ADR 0039：受管应用

状态：接受。2026-11-24。修订 DESIGN INV-6 的"registered 时相同 release_key 是空操作"：请求体里的 manager 仍然生效。

## 背景

有的应用的发布由平台之外的另一个程序负责：它检查并批准每次变更，自己记录版本和线上的是哪一个。控制台和管理接口可以直接对这个应用发布、移除、清除、丢弃，改它的访问、策略、owner 和租户。这样做绕过了那个程序的检查，它的记录也和线上对不上。平台没有办法表达"这个应用的发布属于别人"。

## 方案

1. **只在控制台隐藏或警告。** 改动最小，但管理接口和 `appctl` 照样能写，任何直接调用接口的脚本都绕得过去。
2. **把管理方绑定到一个认证主体。** 只有管理方的主体（例如它的令牌）能写。`local` 模式没有认证，调用者都是平台管理员，这条规则在那里无从执行；`upstream` 和托管模式要给管理方发令牌、规定它和租户角色的关系，等于在 ADR 0022 的授权之外再造一层。管理方停用或出错时，人也没有显式的出口。
3. **Manifest 字段。** manifest 是应用的契约，随 bundle 走，说应用要什么，不说谁运营它。放进去后，同一份源码换一个运营方就要改源码；在控制台发布一份不带这个字段的 manifest 就能去掉标记，正是要防的操作。remove、purge 和改访问也都不带 manifest。
4. **点名管理方。** manager 是 App 的属性，和 owner 并列。对受管应用的每个写请求都要带上 manager 的名字，不带或名字不对就答 409，说明管理方和去哪里操作。这不是认证：名字谁都能写。管理方自己的调用这样通过，人确实要绕过它时也这样显式覆盖。

选方案 4。

## 决定

1. **App 的属性。** App 多一个 `manager`：`name`（文法同应用名）和可选的 `url`（`http` 或 `https` 的绝对地址，至多 2048 个字符，人去那里经管理方操作）。没有管理方的应用为空。列表和详情返回它。
2. **点名放在请求头。** 写请求用 `X-Pneuma-Space-Manager: <name>` 点名。不用请求体：remove、purge、discard 没有请求体（purge 只在托管模式有），policy 的请求体就是补丁本身。请求头在每个路由上是同一个位置，现有请求体一字不改，不读请求体的路由也不用开始解析。`appctl` 的 `--manager <name>` 发送它，控制台在人输入名字后发送它。
3. **哪些写要点名。** 对受管应用：publish、remove、purge、discard，改 policy、access、owner、tenant，以及清除 manager。不带请求头或名字不同，答 409，什么都不改，消息写明管理方和它的 `url`、在这里操作会绕过它、怎样点名。授权不变：先按 ADR 0022 判定，403 和 404 先于 409。非受管应用忽略这个请求头。
4. **运维不受限。** stop、restart、kill、unquarantine、日志、状态、指标和所有读都不用点名。平台自己发起的动作也不用：临时应用的到期清扫（ADR 0038）、续跑 purge、启动收敛。全局策略不是对某个应用的写，也不受限。
5. **设置、更换、清除。** 发布请求体的 `"manager": {"name": n, "url"?: u}` 定下发布之后的 manager。首次发布可以设；非受管的已有应用由一次带它的发布变成受管，权限与发布相同。更换是对受管应用的写，要点名当前的 manager。没给 `url` 时，名字不变则保留原来的 `url`，名字变了则为空。请求体没有 `manager`（或为 `null`）时 manager 不变，漏写不会清除它。清除只有一个显式入口 `DELETE /api/apps/<name>/manager`（`appctl unmanage <name>`），同样要点名，动作与发布相同（`app.release`，托管令牌要 `publish` 范围），审计为 `app.manager`。相同 `release_key` 的发布不写 Release，请求体的 manager 照常生效。
6. **审计。** 带这个请求头的写，审计行的 details 记 `namedManager`，点名的人就是这一行的 actor。`app.publish` 的 details 记请求体的 `manager`。被拒绝的写照常记为 `refused`。
7. **控制台。** 项目卡片和详情显示管理方，有 `url` 时是链接。受管应用的发布、移除、清除、改访问、移租户和改策略都不隐藏；它们的确认卡片说明应用由谁管理、在这里操作会绕过它，人输入管理方的名字后才能继续，请求随后带上这个名字。
8. **与临时应用独立。** 两个属性互不影响，临时应用也可以受管。

## 后果

- 这是防误操作的护栏，不是安全边界。名字不是秘密，列表里就看得到，任何有写权限的调用者都能带上它。谁能做什么仍然只由授权决定。
- 管理方得不到通知。有人点名绕过它时，它要从审计的 `namedManager` 或列表里发现。
- 能发布的人都能把非受管应用标为受管，点名后也能更换或清除 manager；清除之后，管理方下一次带 `manager` 的发布会重新标上。审计记录每一次。
- INV-6 多一个例外：相同 `release_key` 的发布仍可改变 manager。
- 回滚到没有本决定的网关时，旧网关忽略 `manager` 列和请求头，受管应用变成普通应用。
- 不做：管理方的认证、对管理方的回调、在控制台设置或清除 manager。
