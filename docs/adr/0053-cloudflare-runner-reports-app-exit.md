# ADR 0053：Cloudflare 运行器报告应用在启动中退出

状态：暂缓，见 [ADR 0054](0054-cloudflare-runner-image-stays.md)。设计不变，代码已撤回。2026-11-27。补充 [CF 应用契约](../../cf/docs/app-contract.md) 中的失败计数一段；取代 [ADR 0051](0051-cloudflare-only-app-failures-quarantine.md) 后果中“分界靠就绪检查的采样”一条。

## 背景

唤醒时，运行器在解开发布之后启动应用进程。应用进程在就绪之前退出时，运行器关掉自己的 HTTP 服务器，容器随之停止。应用单元分不清这和启动慢，继续探测 `/_pneuma-space/ready`，直到 45 s 的期限。这段时间里这次唤醒占着一个运行名额，请求也一直等着。2026-11-27 在真实部署上，一个启动即退出的应用每次打开都等了 46 s（issue #72）。一个空间只有两个名额时，一个坏应用每次被打开都占去半个空间 45 s。

ADR 0051 只在应用单元看到运行器报告 `unpack` 之后才计入失败。运行器关掉服务器之后不再报告，所以两次探测之间就退出的应用可能不被计入，永远不会被隔离。

## 决定

1. **运行器在应用退出后继续回应就绪检查**，报告里加 `exited: true`，阶段照旧。它不再自行关闭服务器和退出；应用单元结束这次唤醒时销毁容器，平台没有销毁时由容器的不活动超时收回。
2. **应用单元看到 `exited` 就立即结束这次唤醒**，答 503 `startup`（“Application exited before it became ready.”），记一次失败的唤醒，退役并释放名额。
3. **计数规则不变，判断不再靠采样。** 运行器只在解开发布之后才启动应用进程，退出报告里一定带 `unpack`，所以这次失败按 ADR 0051 计入应用自己。
4. **改动最小。** 运行器只改报告的一个字段和退出后的行为；包的格式、取包、解包和代理都不变。之前发布的版本照旧唤醒。没有 `exited` 字段的旧运行器照旧等到期限。

## 被拒绝的方案

- **应用单元在容器停止时结束唤醒。** 要依赖容器的运行状态在启动刚请求时就准确，Cloudflare 没有这样保证；运行器知道应用退出的那一刻。
- **运行器报告退出后再自行退出。** 报告与退出之间又是一个要靠时机的窗口。
- **缩短 45 s 的期限。** 冷启动慢的正常应用会被误判，平台的慢变成应用的失败。

## 后果

- 启动即退出的应用，调用方大约在应用进程退出后一次探测内得到 503，名额随即释放，失败照常计入，到 `maxFailures` 就被隔离。
- 运行器在应用退出后不再自己停止容器，容器存活到应用单元销毁它；应用单元在唤醒中途被驱逐时，下一次唤醒或容器的不活动超时收回它。
- 运行器镜像需要重建，部署时随 Worker 一起推出。
