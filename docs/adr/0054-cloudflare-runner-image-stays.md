# ADR 0054：Cloudflare 运行器镜像暂不更换，ADR 0053 暂缓

状态：接受。2026-11-27。暂缓 [ADR 0053](0053-cloudflare-runner-reports-app-exit.md)，恢复 [ADR 0051](0051-cloudflare-only-app-failures-quarantine.md) 后果中“分界靠就绪检查的采样”一条。

## 背景

ADR 0053 改了运行器，部署时推了一个新镜像。之后真实部署上健康应用的唤醒慢了 0.1 到 0.5 s，14 小时没有恢复。测量见 [验证记录](../../cf/docs/verification.md#runner-image-rollout-2026-11-27)：

- 探针应用报告自己所在机器的 CPU。快的唤醒都在 AMD EPYC 9684X 上，慢的都在 AMD EPYC 7713 上；同一个应用的各次唤醒机型相同。
- 用了两天的旧镜像，17 个应用里 12 个在 9684X 上。几分钟前推的第三个镜像，8 个应用全在 7713 上。ADR 0053 的镜像 14 小时里 25 次采样共 300 次唤醒，只有 16 次是快的。
- 新旧镜像只差 20 KB 的一层，在同一台机器上交替运行一样快。

慢的不是运行器的代码，是 Cloudflare 给新镜像安排的机器。原因未知；新镜像会不会随时间换到快机器，也未知。

## 决定

1. **唤醒时间优先。** 打开一个睡着的应用是这个平台最常见的请求，启动即退出的应用是少数。运行器恢复成 ADR 0053 之前的文件，部署时构建出原来的镜像；应用单元、契约和验收行 CF-39 一并撤回。
2. **ADR 0053 的设计保留，暂缓。** 重新启用的前提是：新镜像在承接唤醒之前先量过，所在机器不慢于当前镜像。做法见 issue #76，另立 ADR。
3. **`cf/runner/` 在此之前不改。** 任何字节的变化都是一个新镜像。

## 被拒绝的方案

- **留着新镜像等它变快。** 14 小时没有变，也没有依据说会变，这期间每次唤醒都付这个代价。
- **应用单元从“运行器答过又不答了”判断应用退出。** 不用换镜像，但分不清应用退出和平台收走容器，会把平台的故障记到应用头上，正是 ADR 0051 要避免的。

## 后果

- issue #72 的行为回来了：启动即退出的应用，调用方等满 45 s，这期间占着一个运行名额；在两次探测之间退出的应用可能不被计入失败。
- 旧镜像也不保证在快机器上，这次 17 个应用里有 5 个在慢机器。唤醒时间取决于 Cloudflare 的机器，平台能做的只是不去触发已知的变慢。
- 安装器靠本机的构建缓存重现原来的镜像。全新的检出或清过缓存的机器可能构建出不同的一层，那就是新镜像。
- 第一次安装没有旧镜像可用，从新镜像被安排到的机器开始。
