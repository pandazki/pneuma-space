# ADR 0040：升级时管理写只进最新构建

状态：接受。2026-11-24。修订 ADR 0025 第 8 条：新旧副本除了共用一个 schema，管理写和领导权只归最新的构建。

## 背景

网关多副本按滚动发布升级，一段时间里新旧代码同时服务，连同一个库。ADR 0025 第 8 条让迁移只做加法，保证旧代码在新 schema 上不出错；新版本加的规则却只在新代码里，落到旧副本的写不检查它，旧副本当领导者时也不执行它。ADR 0038、0039 上线时就是这样：旧副本上的写可以不点名就改受管应用、把临时应用的访问放宽、把临时应用算进 `apps`，旧领导者不做到期清扫。逐个 ADR 补兼容补不全，也没法检查补全了没有。

## 方案

1. **停机发布。** 网关用 `Recreate`，新副本全部就绪再放行。没有混跑，代价是每次升级入口都中断。
2. **每个版本声明能和哪个旧版本共存。** 要逐版判断，判断错了就又是上面的问题；滚动发布要等新副本就绪才停旧副本，新副本若等旧副本退出就会死锁。
3. **按请求分。** 应用流量和读由任一副本处理，管理写和领导权只归最新构建。

选方案 3。

## 决定

1. **构建号。** 网关启动时对自己的源码（`gateway/src` 和 `shared`）算 sha256，取前 12 位写进 `replica` 行的新列 `build`，不用人维护版本号。
2. **当前构建。** 活副本（`seen_at` 在 10 s 内）按 `build` 分组，每组取最早的 `started_at`，这个时刻最晚的一组是当前构建。最后上线的构建总是当前构建，回滚也一样；只有一种构建时就是它。
3. **管理写。** 管理 API 里 GET 之外的路由，先读 `replica` 表判断当前构建；本副本不在当前构建上就答 503，带 `Retry-After: 2`，消息说平台正在升级、几秒后重试，什么都不改，也不写审计。入口端口上的应用流量、管理 API 的 GET 和 `/healthz` 照常由任一副本处理。
4. **领导权。** 不在当前构建上的副本不再争领导锁，持有时在下一次心跳释放。新构建的副本在随后的心跳里取锁，到期清扫和其他周期工作约 2 s 内交给新代码。
5. **客户端。** `appctl` 遇到带 `Retry-After` 的 503 按它重试，至多 30 s；负载均衡可能再选到旧副本，所以按次数重试。控制台显示这条消息，人再点一次。
6. **单机。** 只有一个副本，规则不起作用。

## 后果

- 混跑窗口里管理写的结果和全部升级完以后一样，代价是落到旧副本的写短暂答 503。新版本加的规则只写在新代码里，ADR 不再逐条说明混跑时怎样。ADR 0038 第 5 条为旧网关建的租户行补默认值已不必要，留着不删。
- 应用流量仍由旧副本处理，新版本对入口行为的改动在混跑窗口里不保证。一个 App 至多一个实例照旧只靠实例行的条件更新（INV-11），与构建无关。
- 粗糙之处：滚动途中一种构建的副本若全部重启，它会被当成最新的，直到滚动结束；只改部署文件、源码不变时构建号不变，不算升级。
- 不做：入口层按版本路由、人工维护的版本号、runner 的版本混跑（runner 不写平台库）。
