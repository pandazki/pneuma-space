# Cloudflare acceptance

These gates require the deployed CF edition. Local engine checks cannot prove Container, DNS, TLS, browser, R2 CORS or TURN behavior. Use disposable test applications for destructive checks.

| ID | Required behavior |
| --- | --- |
| CF-01 | Owner login reaches /admin; ordinary login reaches /dashboard. Unknown keys fail; no public signup. |
| CF-02 | Invite redemption is once-only under concurrency; expired/revoked invites fail. |
| CF-03 | Tenant cannot read platform APIs or another tenant's apps/data/static/realtime. |
| CF-04 | Control writes require exact Origin and CSRF; cookie-authenticated app writes and WebSocket upgrades require the control Origin. An unauthenticated page navigation to an app redirects to login with its path; other unauthenticated app requests get 401. Logout revokes control and app access. Guest receives no platform credentials or forged identity. |
| CF-05 | Tokens enforce tenant/app/action, expiry/revocation and cannot manage accounts/credentials or purge. |
| CF-06 | Console and CLI/API publish a Node package uploaded directly to R2. The app answers at its path as soon as publication returns. Static publication starts no container. |
| CF-07 | Invalid paths/manifest/digest and failed startup preserve prior working release. Retry creates no duplicate release. |
| CF-08 | SQL/KV/files survive idle, kill, restart and release. SQL cannot read/write hidden platform KV. |
| CF-09 | Old generation/boot writes fail after retirement; concurrent first requests start one container. |
| CF-10 | Remove retains data and denies access; resume restores it. Purge is removed-only, typed, terminal; reused name gets new AppId. |
| CF-11 | Direct R2 PUT/GET matches hashes, denies unsigned/wrong-key access, passes CORS; final purge waits old ticket expiry. |
| CF-12 | Static HEAD/Range, streaming/SSE and WebSocket exchange work with documented lease/drain deadlines. |
| CF-13 | Schedules fire without browser traffic; manual jobs persist IDs/retries/failures and stop after removal. |
| CF-14 | KV CAS/increment are atomic; two authorized subscribers receive publish; undeclared capabilities fail. |
| CF-15 | Projects/versions/data/logs/events/usage/jobs/team/credentials/resources display actual state and working actions. |
| CF-16 | Account disable, invite revoke, membership, quotas and last-admin protection work server-side. |
| CF-17 | Browser verifies Chinese/English, light/dark, 1440/390px, accessible controls and typed purge on both consoles. |
| CF-18 | Actual TURN credentials establish a relay; master key stays private; unconfigured service is honest. |
| CF-19 | Service needs no local server. |
| CF-20 | Quotas and body/result/file limits refuse excess without stopping other apps/control. Diagnostics do not keep idle containers running. |
| CF-21 | The primary tenant flow creates a read/publish/invoke token and gives two steps: a setup command the user runs in a terminal, which stores the token in the new project directory, and an instruction for a coding tool opened in that directory, which holds no token. A clean directory can run the setup command without the platform repository or CF credentials and receive project instructions and skills. The instruction then publishes an interactive durable demo with the project's own commands and obtains its app and dashboard links. Repeating setup preserves user files; credentials and instruction files never enter its package. |
| CF-22 | `start` reports real request timings and states that natural idle was not awaited. The starter benchmark reports real request timings and counter deltas, waits for natural idle as long as the app's policy requires without a sleep action, verifies a new boot and retained data after access, and links to the app's actual dashboard usage. Incomplete idle verification is reported as incomplete. |
| CF-23 | One command given a control domain and a prefix installs from the repository. Without a saved API token it prints a prefilled create-token link and changes nothing in the account. A first install refuses resource names the account already has. Generated configuration and credentials stay in a private directory outside the repository. Rerunning after an interruption resumes without creating anything twice. Rerunning on an existing deployment adds the columns `schema.sql` gained to its database. It ends with the control origin answering over valid HTTPS and owner credentials that sign in. The Worker then holds no account API token, including one an earlier install left. A first install creates D1 and R2 with the location hint of the data center where a request for the control domain, sent from the installing machine through the deployment's own zone, enters, unless `--location` names one; when it cannot measure, it asks for `--location` and creates no data. It records and prints the data's locations and the entry. A rerun over data elsewhere than the entry says so in one line naming `--relocate` and moves nothing. |
| CF-24 | An app is served at `/apps/<name>/` on the control origin; the app receives the path without that prefix and `X-Forwarded-Prefix: /apps/<name>`, and a client cannot supply another prefix. `/apps/<name>` redirects with 308 and keeps the query. Names are unique across tenants. Hosts other than the control origin get 404. An app response cannot widen a service worker beyond its path. |
| CF-25 | A sleeping Node app with a static directory answers `/apps/<name>/` with its `index.html` and other files in that directory without waking; other paths reach Node. The starter's page shell is static: it paints before its API answers and offers a retry in place when the API is slow or fails. |
| CF-26 | Console files are served under `/_pneuma-space/console/` without being marked immutable; `/login`, `/invite`, `/admin`, `/dashboard` and `/downloads/` keep working. Any other root path, such as `/style.css` or `/app.js`, answers 404. |
| CF-27 | A new app sleeps after 300 idle seconds unless its policy is changed; an app created earlier keeps its stored policy. |
| CF-28 | Each wake records the duration of each phase: compute reservation, container start until the runner runs, package fetch, unpack, app listening, readiness confirmation and the first response to the waking request. App detail returns the last wake, events keep one per wake, and the console's runtime panel shows the last breakdown. No test asserts a duration. |
| CF-29 | An app created ephemeral returns its `expiresAt` in list and detail; a TTL over the deployment maximum creates nothing. Uploads and releases that state the other kind answer 409 and write nothing. A token with `remove` discards it from draft, registered or removed; a durable app answers 409 and a discarded one 404. With no caller it ends at `expiresAt`, audited as `app.expire` by `platform` with one `error` row per distinct failure, and a failed end resumes. Its schedules never fire while manual jobs run. It counts toward the editable ephemeral quota, not apps, and gives its slot back as it starts ending while its name and storage stay held until cleanup ends; an end the directory failed to record reaches it on a later alarm. A new space's default storage fits its whole application and ephemeral quotas. Both CLIs publish it with `--ephemeral [--ttl]`, print its id and end, and discard it. |
| CF-30 | A managed app returns `manager` in list and detail. Upload, release, rollback, remove, resume, purge, discard, policy and clearing the manager without its name answer 409 naming the manager, its url and how to name it, and change nothing; runtime actions and reads need no name. Authorization and the request's own errors answer before that 409; a malformed name header answers 400 on any app. A release sets, changes or keeps the manager as ADR 0039 says; `DELETE /apps/:id/manager` clears it with `publish` and is audited. Both CLIs send `--manager`; the console's approval for those writes says who manages the app and sends the name once it is typed, in both languages at 1440 and 390 px. |
| CF-31 | `--relocate HINT` without `--yes` states its plan and what it cannot make safe, and changes nothing. With `--yes` it creates a database and buckets at that hint, copies every D1 row and R2 object, and rebinds and redeploys the Worker only after row counts and digests per table, the audit triggers, object keys, sizes and ETags and every artifact's SHA-256 match; otherwise the Worker keeps the old data. Audit rows and objects that reach the old data after the copy are appended after the switch. An interrupted move resumes on rerun without duplicating rows, and a plain rerun finishes a switch. The old resources stay until `--remove-previous`, which waits an hour after the switch, refuses while the deployed Worker binds them, and finishes on rerun after an interruption. |
| CF-32 | A control write that fails with an unexpected exception answers 500 `internal` with a request id, and the audit keeps that id as `request.error` with the route, the app when known, and the error's name and message; nothing from the request body. |
| CF-33 | `start` and `init` set up a whole project in an empty directory on every Node release line the CLI's `engines` admits. A setup that stopped at any step, including one an earlier CLI left, finishes when the same command runs again and keeps every project file that already exists. A directory counts as an existing project only once its setup has finished. A project an earlier CLI made has finished once it has created an app, and setup adds nothing to it. A non-empty directory without setup state is refused and left unchanged. |
| CF-34 | A Node release with a static directory boots only its files outside that directory: the wake fetches and unpacks no static file, and the container holds none. A release published before ADR 0050 boots its whole package. An upload whose Node entry lies inside the static directory answers 400 `entry` and issues no ticket. |
| CF-35 | A starter project declares each job as a trigger in its manifest and runs it from `app/jobs/<name>.mjs`; packaging refuses a declared trigger without that file, and such a file without its trigger. A delivery runs the job with its id, attempt and payload, a delivery id that already finished answers 200 without running it again, and a job that throws answers 500 and logs its name, delivery and error. The CLI runs a declared job on demand and prints its outcome and the app output since, and lists the declared jobs, the last 10 deliveries and the last 20 lines of app output. A token with `publish` or `manage` runs a declared job on demand; one with only `invoke` and `read` is refused. |
| CF-36 | A token created as Create app creates it (read, publish and invoke, every app) is admitted to its app's pages and data paths. The CLI requests a path of the project's own app with GET and that token as a Bearer header, never printing it or putting it in a URL, refuses a path outside the app, and prints the status and the start of the reply. |
| CF-37 | A wake refused because the space already runs its `awake` quota answers 503 `compute_quota` with `Retry-After: 30`, records no wake and counts no failure however often it repeats, and the app wakes as soon as a slot frees. A trigger delivery refused this way is retried 30 s later without using an attempt. Only a wake in which the app's own process does not become ready counts toward `maxFailures`: a wake that fails before the app runs is recorded without counting, a successful wake clears the count, and a publication whose release does not start leaves the previous release's count unchanged. |
