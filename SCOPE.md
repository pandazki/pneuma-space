# Prototype scope and boundaries

This is a local, single-host prototype for people and existing agents to publish small, stateful HTTP applications. Docker Compose runs a gateway; an operator builds a local image and publishes it by name. The gateway starts an application on first request, stops it after idle time, and mounts a persistent volume at `/data`. Samples support SQLite and PostgreSQL through a JSON-record CRUD interface and a small parameterized relational transaction adapter. Only common SQL and tested business semantics are portable; it is not a general SQL compatibility layer. App URLs survive container stops and gateway restarts.

The app contract is intentionally small: an image listens on HTTP port 8000, stores durable files under `/data`, and serves relative URLs under a stripped URL prefix. An app can read `X-Forwarded-Prefix` for its external base path. The platform does not promise database portability: SQLite and PostgreSQL have different concurrency and SQL semantics; selecting a backend does not migrate existing data, and applications must plan migrations explicitly. SQLite is local-file storage and is not a multi-node database. PostgreSQL schema selection alone (including search_path) is not a security boundary; isolation requires distinct, least-privilege roles and grants and an appropriate tenant design.

This prototype is **only for a trusted operator and trusted application images on a local machine**. The gateway controls the Docker daemon, which effectively grants host-level control. Apps share a Docker network and can reach the gateway and each other. Loopback port bindings are not authentication, and do not isolate containers from one another or defend against a malicious local process. Do not expose either port to the internet or deploy untrusted tenant code. There is no user authentication, authorization, tenant isolation, TLS, resource quota, secret management, backup, audit trail, or protection against denial of service.

A future enterprise implementation needs a trusted identity boundary, server-side identity propagation, workload isolation, lifecycle and recovery policies, and auditable operations. A hosted multi-tenant service additionally needs tenant isolation across compute, network, data and control plane, metering, abuse prevention, and operational cost validation. None is implied by this prototype.

Current limits: HTTP request/response only (no WebSocket, streaming, built-in scheduler, or background job guarantee); request and response bodies are buffered and limited to 8 MiB; apps must be ready within the startup timeout and tolerate being stopped when idle. Idle time is measured from completion of the last request. Volumes survive redeploy and removal of a registration; operators own backup and cleanup. Published images are trusted and must already exist locally. This is not a scheduler or production runtime.
