# 03 · 有界冷应用和并发唤醒实验

目的：在现有机器上了解原型行为，并保护其他工作负载；这不是容量测试或性能承诺。[before.json](before.json) 和 [after.json](after.json) 保存 2026-11-04 修复前后的单次原始结果。脚本运行的是当前修复后版本；修复前结果是历史记录，仓库没有保留可直接重跑的旧实现。

从项目根目录启动网关后执行：

```sh
python3 prototype/03-cold-apps/probe.py
```

需要可用的本地 Docker、运行中的 Compose 网关和已缓存的 `python:3.12.12-slim`。脚本先检查基础镜像已缓存，缺失时直接退出；未监测构建器是否访问远端元数据。它创建唯一命名的测试镜像、24 个已登记的停止容器和卷，最多启动 3 个测试应用，以最多 9 个并发请求运行后删除本次资源。不会碰其他应用卷。异常中断可能遗留以 `load` 和 `appbase-loadtest` 开头的唯一资源，应先核对归属再清理。

安全上限是测试规模限制：24 个冷应用、最多 3 个同时运行、最多 9 个请求。脚本在取样时以网关 128 MiB、单个测试应用 64 MiB、耗时 180 秒为停止阈值，**不是 Docker cgroup 的硬限制，也不是连续监测或强制超时**。执行前发现机器已有其他长期运行容器，因此没有扩大规模。测试不会控制其他容器或背景负载。

## 观察

| 指标 | 修复前单次 | 修复后单次 |
| --- | ---: | ---: |
| 网关基线内存 | 11.07 MiB | 15.41 MiB |
| 登记 24 个冷应用后网关内存 | 11.13 MiB | 15.44 MiB |
| 三个不同应用并发冷启动 | 327.8 / 427.6 / 512.5 ms | 290.6 / 299.4 / 307.6 ms |
| 热请求，依次执行 | 10.5 / 8.7 / 11.7 ms | 10.0 / 9.7 / 10.5 ms |
| 网关基线文件描述符 | 5 | 5 |
| 并发保持请求期间文件描述符快照 | 17 | 21 |

同一冷应用同时收到三个请求时，修复后均成功，本次各约 496 ms。测试应用的保持请求故意等待 1.5 秒；连接快照在等待期间记录到 8 个 ESTABLISHED 服务端连接，非峰值。TCP 状态是网关网络命名空间内的瞬时快照，不是全机连接数。应用内存的单次读数约 9.68–13.79 MiB；Docker daemon、磁盘、文件系统缓存和主机其他进程不包含在网关容器内存里。

发现的问题：原网关在全局注册表锁内启动 Docker 容器，使不同应用启动排队；管理列表也在锁内执行逐容器查询。修复后启动和列表查询不再持有全局锁，活跃请求先占位，仍可防止启动期间被移除或闲置停止。回归测试见 `tests/test_runtime.py`。闲置停止本身仍持锁，管理列表仍要逐个查询 Docker，后续需要重新设计状态和观察机制。

两次基线内存不同，且每种条件只有一次、并发度低，不能把数值差异解释成可靠提升。不能据此外推几百或几千个应用、不同机器、Kubernetes、租户隔离、费用或长期稳定性。

## 对热请求波动的分阶段定位和修复

在相同 24 个冷注册／3 个活动测试应用的限制下，使用仅通过 `APPBASE_TRACE=1` 显式开启的响应头采集网关阶段时间，测试后已恢复默认关闭。脚本 [diagnose-replica.py](diagnose-replica.py) 保留每个请求的时间线和资源快照；单应用对照见 [diagnostic-before.json](diagnostic-before.json)。

- 修复前，[diagnostic-replica.json](diagnostic-replica.json) 中一次热请求客户端耗时 685.69 ms，其中网关获取应用阶段为 682.96 ms。进一步拆分的 [diagnostic-split.json](diagnostic-split.json) 中，一次热请求客户端 233.42 ms，Docker 启动调用 180.21 ms，注册表锁约 0.01 ms，连接和应用响应分别低于 1 ms。此前网关即使应用已运行也会对每次请求调用 Docker start。
- 修复后，网关对已知运行容器复用状态；冷启动仍通过 Docker，空闲停止会清除状态。连接失败时只在 HTTP 请求发送前尝试恢复，避免重放写请求。修复前后原始记录为 [diagnostic-split.json](diagnostic-split.json)、[diagnostic-fixed.json](diagnostic-fixed.json) 和 [diagnostic-fixed-2.json](diagnostic-fixed-2.json)。相同应用的并发冷启动、外部停止后恢复和闲置停止／唤醒均已实际测试。
- 三轮额外客户端分段采样 [1](diagnostic-client-stages.json)、[2](diagnostic-client-stages-2.json)、[3](diagnostic-client-stages-3.json)，每轮 63 个顺序热请求。第一轮客户端范围 1.59–13.09 ms，第二轮 1.41–201.13 ms，第三轮 1.31–4.69 ms。第二轮最慢请求在客户端等待响应头约 200.67 ms，网关记录的处理时间约 16.90 ms。差额包括网关处理函数开始前、响应写回、容器转发和客户端调度等阶段，现有数据**不能确定具体原因**；不能将少量样本解释为吞吐或延迟保证。
- 外部直接停止容器后，[diagnostic-dns.json](diagnostic-dns.json) 的一次停止状态 DNS 查询约 4.0 秒后失败，首次访问恢复约 4.3 秒。平台自己进行闲置停止时会主动清除缓存，因此走正常冷启动；外部停止后虽成功恢复，长 DNS 等待仍是已知风险。

时间均为单机样本，资源指标是阶段性 Docker 容器快照，不包括 Docker daemon 的完整资源消耗；阈值不是硬配额。故障恢复、重放安全和长时间／大规模负载还需后续工作。
